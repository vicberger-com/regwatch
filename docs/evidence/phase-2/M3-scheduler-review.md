## Data flows touched
- **Editor or admin to API:** `POST /capture-jobs/{id}/run-now` (gate `sources.manage`); saving a source or job sets `next_run_at` from the job's cron or interval and time zone.
- **Reader to API:** `GET /capture-runs` and `GET /sources/{id}/health` (gate `sources.read`): run rows, `error_class`, `error_message`, `last_error`.
- **API and worker to Valkey:** `capture.run_job(job_id)` published with a countdown (jitter); the worker's remote-control mailbox; Beat publishes the two periodic tasks.
- **Worker to PostgreSQL:** `capture_run` rows created, claimed (`FOR UPDATE SKIP LOCKED`), finished; `capture_job.next_run_at` and `last_run_at`; `source.health` and `consecutive_failures`.
- **Beat to its local file:** `/tmp/regwatch-beat-schedule` (`shelve`, i.e. pickle).
- **Trust boundary:** request fields; anything readable from the broker (any process on the `regwatch` network, since the dev `REGWATCH_QUEUE_URL` has no credentials); the Beat schedule file; the time zones the image's tzdata knows.

## Findings
| # | Severity | Description | Fix PR | Verified |
| --- | --- | --- | --- | --- |
| 1 | medium | **Beat loads a pickle from a fixed name in world-writable `/tmp`.** `entrypoints.py:17,35` passes `--schedule /tmp/regwatch-beat-schedule` to Celery's default `PersistentScheduler`, which opens it with `shelve` (`celery/beat.py:583-584`), and reading `entries` unpickles it. In the container `/tmp` is private, but the same entry point run on a host (`uv run regwatch-beat`) uses the shared `/tmp` (mode 1777 here), where any local user can create the file first. **Failure case** (`beat_pickle_poc.py`): a planted `regwatch-beat-schedule.db` whose `entries` is a `__reduce__` to `os.system` runs `id` the moment the scheduler starts, as the Beat user, who holds the database and broker credentials. The persistence is not needed: the two periodic tasks are idempotent and job schedules live in PostgreSQL. **Fix:** use an in-memory scheduler (a `celery.beat.Scheduler` subclass passed with `--scheduler`, which persists nothing), or at least a directory owned by the service user with mode 0700 (for example under `$XDG_STATE_HOME` or `/var/lib/regwatch`), refusing to start if it is group or world writable. Update the entry point test, which currently asserts the `/tmp` path. | | |
| 2 | medium | **Publishing to the broker has no timeout, so a broker that accepts but does not answer blocks run-now and the tick forever.** `tasks.py:34-40` calls `send_task` in `anyio.to_thread`; `worker.py:32-48` sets no `broker_transport_options`, and kombu's Redis transport defaults `socket_timeout` to `None` (`kombu/transport/redis.py:1072`). **Failure case** (`blackhole_poc.py`): with a listener that accepts and stays silent, `enqueue_run` was still blocked after 45 s, when the probe gave up; the thread stays stuck. Run-now has already committed its run, so the job's next run-now returns that run and the source is held until the sweep. Each hung request keeps one of anyio's 40 default threads, which `core/security.py:52,56` also uses for password hashing, so about 40 hung run-nows (one per job; an editor can create the sources) stall every login. In the worker, a hung tick holds one of the 2 processes; two hang the whole capture queue. **Fix:** set `broker_transport_options={"socket_timeout": 5, "socket_connect_timeout": 5}` and `broker_connection_timeout`, pass a bounded `retry_policy` to `send_task` (for example 2 retries within 5 s), and wrap the hand-over in `anyio.fail_after` with its own `CapacityLimiter`, treating a timeout like the existing `queue-unavailable` path. Test with a silent listener, not only a raising stub. | | |
| 3 | medium | **One job whose schedule cannot be computed stops every job.** `tick` computes `_advance` for each claimed job inside one loop and one transaction (`runs.py:48-49,63-71`); an exception from `ZoneInfo` or `parse_cron` aborts the whole tick, commits nothing, and repeats every minute. **Failure case** (`test_poc.py::test_e`): a cron job with an unknown time zone and a healthy job both due: the tick raises `ZoneInfoNotFoundError` and starts neither. This is not hypothetical: the host accepts `US/Eastern`, but the `regwatch-api:dev` image (python:3.12-slim) does not (`ZoneInfoNotFoundError`), so a job saved by an API with fuller tzdata, a restored backup, or a base image update that drops a legacy name silently stops all capture. **Fix:** handle each job separately: on failure log it, set `next_run_at` to `NULL` (or disable the job) and record a `failed` run with `error_class="bad-schedule"`, then continue. Also normalise the stored zone to a canonical key at save. Add a test with one bad and one good job. | | |
| 4 | medium | **A lost message holds the source for 2 to 3 hours and is then counted against the source.** ADR-0006 decision 2 and its consequences ("Messages lost from Valkey are re-enqueued on the next tick"; "A broker loss costs at most one tick") are not met: when a job is due and its run is unfinished, `tick` only moves `next_run_at` on (`runs.py:66-67`), and only the hourly sweep ends the run after `ABANDONED_AFTER` (2 h, `runs.py:37,181-193`). `abandoned` and `queue-unavailable` are then counted as source failures (`runs.py:118,190`, `finish` 148-154). The owner accepted a broker with no persistence (ADR-0006 Q2), so every Valkey restart loses all queued and countdown-held messages. **Failure case** (`test_poc.py::test_d`): a tick hands over a run, the message is lost; ticks at +1 h and +2 h start nothing; the sweep ends the run and the source becomes `degraded` with one failure, though it was never fetched. Five Valkey restarts in a row would mark every source `unhealthy` and put them in the digest. **Fix:** in the tick, when a due job has an unfinished run older than the jitter plus a margin (for example 5 minutes) that no worker holds (probe it with `FOR UPDATE SKIP LOCKED`; a running worker holds the row lock from `claim`), re-enqueue it. Do not count infrastructure classes (`queue-unavailable`, `abandoned`) in `consecutive_failures`. Amend ADR-0006 rather than only adding an ASSUMPTIONS row (finding 8). | | |
| 5 | low | **`next_cron` can return a time before `after` in a repeated (fall-back) hour, so the job runs on every tick until the wall clock passes it.** `schedule.py:99-111` builds the floor from the wall time and picks the first candidate with `fold=0`; when `after` is in the second occurrence, that candidate is an hour earlier in UTC. The docstring says "strictly after". **Failure case** (`dst_hammer.py`, America/New_York, 2026-11-01): a `*/15` job saved at 01:16 EST gets `next_run_at` 01:30 EDT, already past; simulated ticks run it 30 times before 02:01 EST instead of once. A daily `40 1 * * *` saved at 01:35 EST runs about 5 times. The same happens when a late tick, a re-enable or a backlog computes from that hour. SafeFetcher's per-host limits bound the request rate, but the run count is wrong once a year per zone. **Fix:** skip candidates whose UTC value is not greater than `after` (`if local.astimezone(UTC) <= after: continue`), keeping "a repeated time happens once"; add the case to `test_time_zones_and_daylight_saving`. | | |
| 6 | low | **Anyone who can reach the broker can control the worker.** `worker_enable_remote_control` is left at Celery's default `True` (`worker.py:33-48`), and the dev broker URL has no credentials (`docs/contracts/env.example:9`, `scripts/dev-env.sh:36`), so every container on the `regwatch` network can reach it. **Failure case** (`broker_poc.py`, against the real `regwatch-worker`): `rate_limit("capture.run_job", "1/h")`, `add_consumer("attacker-queue")` and `shutdown` were all accepted; `inspect stats` and `registered` answered. A rate limit silently stalls capture until the worker restarts. Crafted task arguments only raise (`ValueError` for a non-UUID), and pickle is refused (`ContentDisallowed`), so the worker cannot be made to deserialise code, and the broker password was masked in `inspect conf`, the banner and the logs. **Fix:** set `worker_enable_remote_control=False` (nothing here uses it; `--without-gossip` and `--without-mingle` are already set), assert it in `test_worker.py`, and give Valkey an ACL user and password, used in `REGWATCH_QUEUE_URL`. | | |
| 7 | low | **The sweep releases its own locks after the first run and can overwrite a run a worker has finished.** `sweep` locks all stale runs with `SKIP LOCKED` (`runs.py:185-188`) and then calls `finish`, which commits (`runs.py:156`) after each one, so the remaining runs are unlocked while the loop continues. `finish` updates unconditionally (no `finished_at IS NULL` guard). **Failure case** (`test_poc.py::test_b`): with two stale runs, after the sweep's first commit a worker claims the second (lock free), finishes it as `success`; the sweep then writes `failed`/`abandoned` over it and counts a failure (`degraded`, 1). This needs a message delivered more than 2 hours late during the sweep, for example after a broker outage. No deadlock resulted (`test_poc.py::test_c`): autoflush takes the run lock before the source lock. **Fix:** finish the stale runs without committing between them (a `commit` flag on `finish`, one commit at the end), and make `finish` idempotent (`UPDATE … WHERE id = :id AND finished_at IS NULL RETURNING`, skipping health changes when no row is returned). Test with two or more stale runs. | | |
| 8 | low | **The PostgreSQL run lock is sound but is per job, not per source, and is not enforced by the database.** The deviation from ADR-0006 (lock in PostgreSQL, not Valkey) is a good one: the check runs under the job's row lock in the same transaction that creates the run, it survives broker restarts and has no lease to expire. `test_poc.py::test_a` (4 concurrent ticks and 6 concurrent run-nows) left exactly one unfinished run and one message. But `capture_job.source_id` has no unique constraint (`schema.sql:123-139`), so a second job for a source (a seed, a migration, a future route) would run alongside the first, and any future code that inserts a `capture_run` outside `tick` and `queue_now` bypasses the check. It also loses ADR-0006's re-enqueue property (finding 4). **Fix:** add `UNIQUE (source_id)` on `capture_job` (or lock the source in the tick) and a partial unique index `ON capture_run (job_id) WHERE finished_at IS NULL`, so the invariant holds whatever code writes the row; record the deviation as an ADR-0006 amendment. | | |
| 9 | low | **Run-now has no spacing, and accepts a disabled job.** `queue_now` (`runs.py:79-108`) only refuses a disabled source (`runs.py:90`). **Failure case** (`test_poc.py::test_f`): 40 run-now calls, each after the previous run ended, made 40 runs and 40 audit rows; once connectors land, each is a fetch of a third-party site at an editor's pace. Run-now on a job with `enabled: false` answers 202 and the run ends `skipped`. Saving an interval job's `enabled` or `timezone` also sets `next_run_at` to now (`services.py:259`), another way to start runs at will. **Fix:** refuse run-now (429 with `Retry-After`) when the job's last run started less than a minimum interval ago (for example 5 minutes, or the job's own interval for interval jobs); refuse a disabled job with 409 as for a disabled source; only reset `next_run_at` to now when the interval itself changes. | | |
| 10 | low (latent until connectors) | **A run that kills its worker is retried without limit, and a claimed run holds a transaction for its whole duration.** `task_reject_on_worker_lost=True` (`worker.py:39`) re-queues the message when the child dies; `claim` finds the same unfinished run again, so a page that crashes the worker (memory, a parser fault) is fetched again and again until the sweep ends the run 2 hours later. The M3 notes cap retries at 3 per run. `execute` holds the run's row lock from `claim` to `finish` in one open transaction (`runs.py:159-178`); with a real connector that is a transaction idle for minutes. **Fix:** count attempts on the run (a column, or the message's `redelivered` flag plus a counter) and end it as `failed` after 3; for connector runs, claim with a short transaction that records a lease (`claimed_at`, worker id) and finish in another, rather than holding a lock across the fetch. | | |
| 11 | low (latent until connectors) | **`error_message` and `last_error` are only truncated, not sanitised.** `finish` stores any string cut to 500 characters (`runs.py:142`), and `source_health` shows it to every `sources.read` holder (`services.py`, `source_health`). Today every message is a constant or names only the source kind, so nothing leaks. A connector passing `str(exc)` would put URLs with query-string keys, response text or parser excerpts there, against `schema.sql:149` ("never page content"). **Fix:** make `finish` take an `error_class` from a fixed set and a message built by the connector framework from safe parts (status code, host, byte counts), stripping control characters and URL user info and query strings; add a test that a page body in an exception does not reach `error_message`. | | |
| 12 | low | **Several tests do not prove what they claim.** "One run at a time per source" and "two ticks never start the same job" are tested only sequentially (`test_capture_runs.py:60-68,94-116`); `test_abandoned_runs_are_ended` has one stale run, so finding 7 passes; the DST test covers only an `after` before the repeated hour (finding 5); the broker stub only raises, so finding 2 passes; `test_worker.py` checks the configured `accept_content` but not that remote control is off or that a pickled message is refused; `test_entrypoints.py` asserts the `/tmp` schedule path as intended behaviour. **Fix:** add the concurrency case from `test_poc.py::test_a`, two stale runs, an `after` inside the repeated hour, a silent-listener broker, `worker_enable_remote_control is False`, and one bad plus one good job in a tick. | | |
| 13 | info | (a) `next_cron` treats a naive `after` as the host's local time (`schedule.py:99`); every caller passes UTC, but an assertion would keep it so. (b) A day-of-month such as `*/2` counts as restricted, so `0 0 */2 * MON` matches odd days or Mondays; Vixie cron treats a field starting with `*` as unrestricted (AND). Document or align. (c) `tzdata` entered `uv.lock` with Celery but only for `sys_platform == 'win32'`, so it is not installed and needs no register row; the project relies on the image's system tzdata (see finding 3). (d) `GET /capture-runs` counts the whole filtered table on every request; fine now, an index-only estimate may be needed as runs accumulate. (e) Registries list the event `source.unhealthy` for M3; nothing emits it yet. (f) Celery logs the full body of a refused message (`Received invalid task message … full contents`), up to the message size; harmless for these tasks. (g) `ZoneInfo` accepts `posixrules`, `Factory` and `right/…` (leap-second) zones; consider allowing only `zoneinfo.available_timezones()`. | | |

## Checked and found fine
- **Deserialisation:** `task_serializer` and `accept_content` are JSON only, and the control mailbox takes `accept_content` (`celery/app/control.py:442`); a pickled message to the `capture` queue was refused with `ContentDisallowed` and discarded. No result backend.
- **Crafted task arguments:** `capture.run_job` with a non-UUID or an object raises in `uuid.UUID` before any database work; a valid UUID with no unfinished run does nothing. Only the three contract tasks (and Celery's built-ins) are registered, and their names match `registries.yaml` (test).
- **Broker credentials:** masked as `redis://:**@…` in the worker banner, Beat's banner, connection logs and the `inspect conf` reply (`********`); the `queue-unavailable` path writes a constant message and swallows the exception text.
- **Concurrency:** concurrent ticks and run-nows produce one unfinished run and one message (`test_poc.py::test_a`). A duplicate message finds nothing to claim (`SKIP LOCKED`, test). A live run holds its row lock, so the sweep skips it. The lock order (source, then job; runs before the source in `finish` because of autoflush) gave no deadlock in the scenarios tried, including the sweep racing a worker.
- **Crash between commit and enqueue:** the run row exists and nothing is double-started; the cost is finding 4.
- **Authorization and audit:** run-now needs `sources.manage` (viewer 403, test), the read routes `sources.read`. The audit row `capture_job.run_now` carries actor, IP, run and source, in the run's transaction; returning an existing unfinished run writes no second row.
- **Cron cost:** fields capped at 200 characters and checked by range; a schedule that never fires costs about 2 ms over the 8-year search, 200 of them 0.21 s; a firing schedule returns on its first matching day. Jitter is 0 to 30 s and the batch 200 per minute.
- **Time zones:** keys with `..`, absolute paths, NUL or 6,000 characters are refused by `ZoneInfo` as `ValueError` or `KeyError`, both caught at save (422). Spring-forward times are skipped and a repeated time is taken at its first occurrence when computed from before it (tests).
- **Listeners:** the worker (`--without-gossip --without-mingle`, prefork, 2 processes) and Beat opened no listening socket; both only connect out to Valkey and PostgreSQL.
- **License evidence (`license_check.sh`):** every tag in R-01 C4 to C16 resolves to the cited commit on GitHub, and each LICENSE text is what the row says: BSD-3 for Celery (its `docs` CC BY-SA 4.0 paragraph is in the LICENSE), kombu, amqp, billiard, vine, click-plugins and prompt-toolkit (none has an advertising clause); MIT for click-didyoumean, click-repl, wcwidth (plus Markus Kuhn's no-conditions notice), six and tzlocal; Apache-2.0 and BSD-3 for python-dateutil. The six exceptions in `scripts/license-exceptions.toml` match the locked versions and the commits. The packages added to `uv.lock` are exactly those rows plus `tzdata`, which is Windows-only (finding 13 c).
