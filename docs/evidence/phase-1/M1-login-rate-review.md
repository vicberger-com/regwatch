## Checked and found fine
1. **Every failure path in `login()` is counted and only success is refunded.** The attempt is counted at `services.py:377` before any `await`; `forgive_login` runs only at `:425`, after the session is committed. Not refunded, therefore counted: unknown email, account without a password hash, disabled account (`:385-399`, both the 401 and the 423 from `unknown_locks`); locked account with any password (`:401-405`, so a correct password during a lock is not an oracle and does not refund); wrong password, including the one that triggers the lock (`:409-412`); any exception before `:425`, including a failed `auth_settings` query, a row-lock or pool timeout and a failed commit (fail-closed). An expired lock followed by a correct password unlocks and refunds, which is a real success. An exception after `:425` (`roles_and_permissions`) refunds a sign-in whose password was correct; that is not a guess.
2. **Every failure path in `change_password()` is counted.** The hit at `:456` precedes all awaits; the refund at `:462` runs only when the current password verifies; a vanished user (`:459-460`), a wrong current password (`:463-468`, which also feeds `_count_failure` and the lockout) and any exception before the verify stay counted.
3. **Bursts.** Both checks and hits are synchronous with no `await` between count and hit, so on the single event loop concurrent requests are serialised at the counter: the sixth parallel request on an account, or the 31st on an address, is 429 even while earlier ones are still verifying. In-flight successes count too, so they cannot be used to burst. The API runs one uvicorn process (`api/main.py`, no `workers`); with more workers each process would keep its own counters (BL-65, documented).
4. **Refunds cannot reset the counters by alternation.** Proof of concept: alternating a correct sign-in to an own account with wrong passwords for other accounts from one address admitted exactly 30 failures, then 429 at request 60, address count 30; alternating correct and wrong passwords on the same own account admitted exactly 5 failures. A success adds one hit and removes one, so it is net zero; the only leak is the timing skew of finding 1.
5. **Lockout interaction.** The lockout is untouched and still caps guesses per real account at 10 per lock cycle (10 in 15 minutes, then a 30-minute lock that also ends sessions), well below the 5-per-minute account limit over any long period; unknown emails mirror it through `unknown_failures`/`unknown_locks`. The account key is the lower-cased, stripped email digest, so case and whitespace variants share one budget, and the lookup by exact email cannot reach a real account through a variant. Password-change failures no longer draw on the sign-in budget but still count toward the same lockout, so a stolen session plus sign-in attempts together still get at most 10 guesses per cycle.
6. **Password-change limit.** Keyed on the user id, so it cannot be bypassed by changing address or session; cleared in both test fixtures. No other route verifies a password (`verify_password` is called only from `identity/services.py`). The only unthrottled paths are the correct-password ones in finding 2.
7. **Client address.** `request.client.host` comes from uvicorn's proxy-headers handling with `trusted_proxies` defaulting to exactly the Compose proxy (`10.89.0.2/32`, BL-73), so the per-address limit is per client, not site-wide, in the shipped configuration.
8. **Documentation.** CHANGELOG entry, BL-83 note and the code comments at `services.py:44-49` and `:177-182` state the same numbers as the code.

### Regression checks
- **Burst gap:** none. `_check` checks every limit, then counts them all with `hit_at` in the same synchronous step, with no `await` in between (`services.py:232-242`). In `v3.py`, 50 concurrent coroutines on one account each awaited after the check; 5 were admitted and 45 got 429. Moving the never-refunded cap from count-first to check-first keeps its bound of 20: the check is `>= limit` before counting, where it was `> limit` after.
- **The changes to `count` and `retry_after` do not affect `unknown_failures`.** The lockout path uses only `unknown_failures.hit(key) >= threshold` and `reset(key)` (`services.py:475-477`). `hit` still creates the entry through `_prune`, and the dummy Argon2 verify and the `unknown_locks` check are unchanged. Deleting an empty entry in `count` only moves the key to the end of the insertion order when it is next hit. Eviction does affect this window, though; see N4.
- **Evicting the oldest keys at the cap can reset someone else's counters (N4).**
