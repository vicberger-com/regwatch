# Development stack

```
make dev     # creates deploy/.env on first run, builds the api image, starts the stack
make stop
```

- `http://localhost/` serves the SPA; `http://localhost/api/v1/health` and `/api/v1/version` go through `proxy` (Caddy) to `api`; every other path goes to the Vite dev server (`web`).
- Mailpit UI: `http://localhost:8025` (bound to 127.0.0.1).
- Optional sidecars: `docker compose -f deploy/compose.yaml --profile search --profile translate up`.
- `deploy/.env` is generated by `scripts/dev-env.sh` from `docs/contracts/env.example` with a random secret key and database password. It is git-ignored; `scripts/dev-env.sh --force` recreates it (the database volume keeps the old password, so also run `docker volume rm regwatch_pgdata`).
- Only `proxy` publishes ports (80, 443) and `mailpit` publishes 8025, all on 127.0.0.1, so the stack is reachable from this machine only; from elsewhere use an SSH tunnel (`ssh -L 8080:127.0.0.1:80 host`). All other services sit on the internal `regwatch` network, which has no route to the internet.
- The `regwatch` network is pinned to `10.89.0.0/24` with `proxy` at `10.89.0.2`, and `make env` sets `REGWATCH_TRUSTED_PROXIES=10.89.0.2/32`, so the API trusts `X-Forwarded-For` from Caddy and from nothing else, and sees each client's address for login limits and audit rows (BL-73). If the subnet collides with a host network, change the subnet, the proxy address and the variable together; a unit test checks that they agree.

## Opening the stack through an HTTPS proxy (DevSpaces, AgentSpaces)

The proxy publishes only on 127.0.0.1. To use it from your own browser on a cloud devbox, open
it through the devbox's owner-only, Midway-authenticated proxy URL instead of widening the bind:

1. Open the devbox's proxy URL for port 80: `https://$(cat /etc/devspace/id)--80.$(cat /etc/devspace/http-proxy-base-domain)/`. That address stays in your browser's address bar, but the proxy delivers requests to the devbox under another host name (`e-…--80.…`); the dev server's "Blocked request" page names it.
2. In `deploy/.env`, set `REGWATCH_BASE_URL` to the address-bar URL (the browser sends it as `Origin`, and the API accepts mutating requests only from that origin), and `REGWATCH_DEV_PUBLIC_HOST` to the delivered `e-…` host name alone, so the Vite dev server accepts it. Live reload then runs over `wss:443` to the address-bar host.
3. Restart the web and api containers: `docker compose -f deploy/compose.yaml up -d --build --wait web api`.

Pages then open only through that URL for sign-in: `http://localhost` sends a different Origin, so
the API refuses its sign-in until `REGWATCH_BASE_URL` is set back.

## Database logins (BL-61)

- The API, workers and `regwatch-seed` log in as `regwatch_api`, a member of `regwatch_app`. That role may read and write the application tables but only read and insert `audit_log`, so audit rows cannot be changed or deleted through the application's credentials.
- Valkey (`queue`) requires a password (BL-90 (a)). It lives in `deploy/queue.env`, which only the `queue` container reads, and inside `REGWATCH_QUEUE_URL` in `deploy/.env` for the app containers. Both are written by `scripts/dev-env.sh`. On a setup from before this change, run `scripts/dev-env.sh` once: it adds `deploy/queue.env`, changes only the queue URL line in `deploy/.env`, and keeps the other secrets. Then restart the stack. The queue keeps nothing across restarts, so no data is lost.
- Migrations (`make migrate`) use the owner, `regwatch`, through `REGWATCH_MIGRATION_DATABASE_URL`. That URL and both database passwords live in `deploy/db.env`, which only the `db` container and the one-off `migrate` container (profile `tools`) read; `deploy/.env`, read by the long-running containers, holds the `regwatch_api` login only.
- `deploy/db-init/10-api-login.sh` creates `regwatch_app` and `regwatch_api` (password `POSTGRES_APP_PASSWORD`) when the `db` container starts on an empty volume. A volume created before this change has no `regwatch_api`: run `scripts/dev-env.sh --force` (which also writes `deploy/db.env`), `docker volume rm regwatch_pgdata`, then `make dev`, `make migrate` and `make seed`.
- With `REGWATCH_ENV=production` the API refuses to start if its login holds UPDATE, DELETE or TRUNCATE on `audit_log`; in development it logs a warning.
- Other deployments create the same two roles once, as a superuser or a role with CREATEROLE:
  ```sql
  CREATE ROLE regwatch_app NOLOGIN;
  CREATE ROLE regwatch_api LOGIN PASSWORD '<secret>' IN ROLE regwatch_app;
  ```

## Building behind a TLS-intercepting proxy

The api image build downloads packages from PyPI. If your network re-signs TLS with its own CA, give the build that CA as the optional `build_ca` secret, for example:

```
docker build --target dev --secret id=build_ca,src=/path/to/ca.pem -t regwatch-api:dev api
docker compose -f deploy/compose.yaml up
```

Without the secret the build uses the image's public trust store.

# Production stack (M10.3)

`deploy/compose.prod.yaml` runs the release images: the API's `runtime` target, and the web app built into the Caddy proxy (`deploy/proxy/Dockerfile`). Root filesystems are read-only, with tmpfs only where a process writes. There are no source mounts, no Mailpit and no test printer, and `REGWATCH_ENV=production` is set.

1. **Secrets:** create `deploy/.env`, `db.env` and `queue.env` from `docs/contracts/env.example`, through the secret store, never in the repository.
   - Set `REGWATCH_BASE_URL` to the site's https address.
   - In production the settings refuse `REGWATCH_PRINT_TEST_PRINTER`.
2. **Name the site and the address to publish on:**
   ```
   export REGWATCH_SITE_ADDRESS=regwatch.example.com   # Caddy obtains its certificate
   export REGWATCH_PUBLISH_ADDRESS=203.0.113.10        # 127.0.0.1 unless set
   ```
   Only the proxy publishes ports (80 for the redirect, 443). Publishing on a public address is a deliberate choice. The application is for signed-in users only, and every API route but the health, version, login and public branding routes needs a session. Keep `REGWATCH_PUBLISH_ADDRESS` at 127.0.0.1, behind an SSH tunnel or your own front proxy, until you mean to expose it. On the host's firewall, allow only 80 and 443 from outside: on a rootful Docker host, the host itself can reach the containers' internal addresses (the API on 8000, its metrics on 9464), so keep other users off the host too.
3. **Build and start:**
   ```
   docker compose -f deploy/compose.prod.yaml build
   docker compose -f deploy/compose.prod.yaml up -d db queue
   docker compose -f deploy/compose.prod.yaml --profile tools run --rm migrate
   docker compose -f deploy/compose.prod.yaml run --rm --no-deps api regwatch-seed
   docker compose -f deploy/compose.prod.yaml up -d
   ```
4. **Create the first administrator.** Feed the password on stdin, so it stays out of the shell history:
   ```
   docker compose -f deploy/compose.prod.yaml run --rm --no-deps -T api regwatch-admin create-user --email you@example.org --name "You" --role admin --password-stdin
   ```
5. **Check:**
   - `https://<site>/api/v1/ready` answers `{"ready": true, …}`;
   - the headers include HSTS and the CSP without `'unsafe-inline'`;
   - sign in.
6. **Back up nightly** with `COMPOSE="docker compose -f deploy/compose.prod.yaml" make backup`, and keep encrypted copies off the host (`docs/operations/restore-drill.md`).

The API runs one process a container. Its metrics (port 9464) answer only on the internal networks, for an optional scraper. To use more CPU, scale the `api` service rather than adding processes inside it.

## Sign-in with an organisation's account: the `oidc-test` profile (BL-147; M1b)
A Keycloak with a `regwatch` realm, for development and QA only:
1. `scripts/oidc-test-env.sh http://localhost` (the stack's `REGWATCH_BASE_URL`) writes `oidc-test.env` (for the api) and `keycloak.env` (for Keycloak), both owner-only with fresh secrets. Never commit them.
2. Start the stack with `--profile oidc-test`. Keycloak listens on `127.0.0.1:8190` only. The browser and the api both use `http://idp.localhost:8190`: browsers resolve `*.localhost` to loopback, and on the internal network the name is the container's alias.
3. Turn on `auth.oidc` (Settings, Feature flags).
4. To sign in, an administrator first adds the person with the realm user's email: `oidc-user@example.org` (verified) or `oidc-unverified@example.org` (refused). Their password is `KC_USER_PASSWORD` in `keycloak.env`. Administrators' accounts are never linked by email; they keep their passwords.

The e2e journey: `E2E_OIDC_ENV=deploy/keycloak.env scripts/e2e.sh oidc`, with the usual variables. `REGWATCH_OIDC_TEST_PROVIDER`, which allows plain http, is refused in production.
