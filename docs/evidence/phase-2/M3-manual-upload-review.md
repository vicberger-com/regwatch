## Data flows touched
- **Browser to API:** a holder of `sources.manage` (roles admin and editor) sends `POST /api/v1/sources/{id}/documents`. The body is either JSON `{url, title}` or multipart with a `file` part and an optional `title` field. The body may be up to 10 MB + 64 KB on this path alone, checked before authentication. It is read by the handler only after `authorize` has passed: Origin, session and permission.
- **API, URL:** `validate_source_url` parses the URL and resolves its host with the save resolver, within `DNS_DEADLINE_S`. The API makes no connection to the host (I3). The request `{"kind": "url", "url", "title"}` is stored as `manual/{sid}/{run_id}.json`.
- **API, file:** the bytes are spooled by Starlette (in memory up to 1 MB, then a temporary file), read in full up to 10 MB + 1, and checked by `sniff`. They are stored at `upload/{sid}/{sha256}`, and the request `{"kind": "file", "body_ref", "mime", "sha256", "title"}` at `manual/{sid}/{run_id}.json`.
- **Database:** the `source` and `capture_job` rows are locked, then an unfinished run is looked for. A `capture_run` row is created, with `triggered_by` set to the user, and the audit row `source.document_added` is written, its `after` holding `run_id` plus either `url`, or `sha256`, `bytes` and `mime`. Then commit, then enqueue (`capture.run_job` with the job id).
- **Worker:** `claim` takes the job's oldest unfinished run, and `run_connector` sets `scratch["run_id"]`. The connector reads `manual/{job.source_id}/{run_id}.json` by exact key:
  - A URL goes through `CaptureFetcher` and `SafeFetcher` (robots.txt, the per-host rate, a pinned address on every hop). The body is stored at `raw/{sid}/{sha256}`.
  - A file is read back from `upload/{sid}/{sha256}`, and the key must match that exact pattern for this source.

  HTML goes to the isolated extraction child, plain text is decoded, and PDF is stored as it is.
- **Run manifest to M4:** `raw/{sid}/runs/{run_id}.json`, with `url` (the user's URL, or `urn:sha256:...`), `final_url`, `body_ref` (`raw/...` or `upload/...`), `mime`, `text`, `title` and `metadata.manual`. From there M4 carries it to users' browsers, emails and exports.
- **Trust boundary:** the request body (its URL, title, file bytes, multipart framing and filename) comes from a user with `sources.manage`, so it is less trusted than settings. A fetched body, its headers and its redirects are hostile (8.1). The uploaded bytes are hostile too, because the uploader may simply be passing on a file from elsewhere.

## Checked and found fine
- **The anonymous body cap:** `UPLOADS` raises the cap for `POST` on one path, full match: `/api/v1/sources/` + 36 hex-or-dash characters + `/documents`. Other methods, `/documents/x` and other paths keep 2 MB (tested). No route reads the body before `authorize`: this one declares no body parameter and reads `Request` itself. Through the whole app (`anon_asgi.py`), an anonymous 10 MB multipart request pulls 0 body bytes and gets 401. Without an Origin header it gets 403, and with no `Content-Length` the result is the same. With uvicorn on loopback (`anon_client.py`), the 401 and 403 arrive while the client is still sending, and the connection is closed. The cap only stops a declared length over 10 MB + 64 KB being refused with 413 at once. So an anonymous client can make the server do no more than on any other route.
- **CSRF:** `origin_allowed` requires an Origin equal to `REGWATCH_BASE_URL` on every unsafe method, before the session is read and whatever the content type. A cross-site HTML form posting `multipart/form-data`, a "simple" request with no preflight, is refused like any other.
- **Authorization:** `x-permission: sources.manage` in both the live operation and the contract. A viewer gets 403 and an anonymous client 401 (tested). The source must exist, be `manual`, and have an enabled source and job.
- **Multipart limits:** at most one file (`max_files=1`) and one field (`max_fields=1`); more gives 400 problem details (I6). python-multipart 0.0.33 allows 8 headers per part and 4,224 bytes per header line: nine headers give 400 "Invalid multipart data" (I6), and a 10 MB header flood fails at once with no memory growth (U4a). A file part is spooled to a `SpooledTemporaryFile`, in memory up to 1 MB, so a 10 MB part peaks at about 1 MiB of traced memory (U4c). The context manager closes the file, and the parser closes it on error. A missing `file` part, or a `title` sent as a file, is refused. The filename is ignored: a path as the filename is stored under the content hash (I6).
- **Sizes:** a file over 10 MB is 413 (tested, `upload.read(MAX + 1)`), and an empty one is 422. The 64 KB frame allowance is more than the frame needs, since the title is at most 500 characters.
- **The title:** stripped, at most 500 characters, no control characters, and an empty title becomes `None`. A non-string title in JSON is 422.
- **The API never fetches:** with `socket.connect` and `httpx.AsyncClient.send` trapped, a URL upload makes no outbound connection or request (I3). The save resolver runs in its own pool within `DNS_DEADLINE_S`, as source saves do. Private and unresolvable names and `file:` URLs are 422 (tested).
- **DNS rebinding and redirects at fetch time:** the worker resolves again on every hop, refuses if any address is not public, and connects to the checked address (`fetch.py` `_hop`). U3a: a name that resolved publicly at save time and answers `10.0.0.5` at fetch time is refused as `private-address`, with no request sent. U3b: a 302 to a name that resolves to `169.254.169.254` is refused before it is contacted. Each hop also passes `check_url`, robots.txt and the rate slot in `before_hop`.
- **Object keys:** `upload/{sid}/{sha256}` and `manual/{sid}/{run_id}.json` are built from a parsed UUID (lower case), the hash and the database's run id. `objectstore._path` also enforces its key pattern and refuses dot segments and symlink escapes. The connector builds the request key from `job.source_id` and a run id that must match `[0-9a-f-]{36}`, and accepts a `body_ref` only if it fully matches `upload/{re.escape(source_id)}/[0-9a-f]{64}`. Another source's key, `../../etc/passwd`, an unknown kind or MIME type, and a request that is not JSON are all `bad-request` (tested). No request field can make a worker read another source's upload, and the request object is written only by the API.
- **Runs and races:**
  - Two uploads at once serialise on the source row lock, and the second sees the first's committed run: five at once give one 202, four 409, one upload stored and one hand-over (I1).
  - An upload during a scheduled run is 409 (I2). A due tick after an upload starts no second run, because `tick` locks the job with `SKIP LOCKED` and checks for an unfinished run.
  - Run now within that time returns the upload's run (I2). The worker claims the job's oldest unfinished run, which is that one.
  - A run with no request (a scheduled tick, Run now, a dry run) reads no object and succeeds empty (tested).
  - A run handed over after a lost message still finds its request, because the request is keyed by the run.
- **Order of work:** the title, the URL (DNS included) and the file are checked before any row is locked. The run is committed before it is enqueued, and a refused hand-over ends the run as `queue-unavailable`, so the source is not held.
- **Errors:** every problem text is fixed and quotes no input. Run errors use the existing fixed refusal texts.
- **HTML from either path** is read only in the isolated extraction child, with the job's extraction rules. Plain text is decoded with replacement. PDF is stored for M4.
- **The connector's other checks:** a URL that answers other than 2xx, or with a type other than HTML, XHTML, PDF or text, is refused, and its body is not stored. `scratch["run_id"]` collides with no other connector's key (`listing` only).
