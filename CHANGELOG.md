# Changelog

All notable changes to this project are recorded here. Format: Keep a Changelog; every line ends with issue and requirement IDs. A release section is cut at every phase gate.

## [Unreleased]

### Security
- Final M1 review follow-ups: the start-up check also refuses a login that owns the `public` schema; user display names and role labels are single-line with no control characters; bidirectional override characters count as control characters; CI passes the owner URL to migration steps only (#31, #32, REQ-16)
- The `regwatch` Compose network reserves `10.89.0.128/25` for automatic addresses, so no container can take the proxy address first, and the code and contract default `REGWATCH_TRUSTED_PROXIES` is exactly `10.89.0.2/32` (CP-06); the branding and legal routes refuse control characters, C1 included (#31, #32, REQ-16, BL-73, re-review 5a, 5b, N3b)
- The Compose `regwatch` network is pinned to `10.89.0.0/24` with `proxy` at `10.89.0.2`, and `make env` trusts `X-Forwarded-For` from that address only, so login limits and audit rows see client addresses behind Caddy; the development proxy publishes ports 80 and 443 on 127.0.0.1 only (owner decision on BL-73, review finding 5)
- Owner database credentials move to `deploy/db.env`, read only by the `db` container and a new one-off `migrate` container (profile `tools`, used by `make migrate`); in production the API refuses to start when it holds the owner URL, when its login can alter `audit_log` through any role it can use, at table or column level, or when the check cannot run (#31, REQ-16, BL-61, re-review 6a, 6b, 6c)
- The API logs in as `regwatch_api`, a member of `regwatch_app`, instead of the database owner, so the append-only grants on `audit_log` take effect; migrations use the owner through the new optional `REGWATCH_MIGRATION_DATABASE_URL` (CP-05, owner decision on BL-61); `deploy/db-init/10-api-login.sh` creates both roles; in production the API refuses to start if its login can alter `audit_log`; CI and the integration tests run the application with the same login (#31, #32, REQ-16, BL-61, review finding 6)
- M1 re-review follow-ups: a wrong current password on `POST /auth/password` counts toward the lockout; unknown-account failure counts restart when their lock begins; changing or deleting a role needs every affected permission held; string settings refuse control characters and `general.contact_email` must be an email address; emails refuse control characters (#31, #32, REQ-16)
- Input limits from the M1 review: request bodies over 2 MB answer 413 before any parsing or the session gate; database errors no longer log bound values, and NUL bytes or a lost unique race answer 422 or 409 instead of 500; email syntax, display-name, password, role-list and permission-list limits on input; temporary-password responses carry `Cache-Control: no-store`; the generic settings API applies the branding and legal limits and refuses `branding.logo_ref` (#31, #32, REQ-16, review findings 3, 7, 8, 10, 11)
- Administrators can only grant permissions they hold, and can only update or reset users whose permissions they hold, so a delegated user or role manager cannot escalate; user and role changes take a transaction advisory lock so the last-manager guard cannot be raced; `user.create` audit rows carry the actor IP (#32, REQ-16, review findings 2, 9, 12a)
- Lockout fixes from the M1 review: concurrent wrong passwords on one account are serialised by a row lock so each one counts; locked accounts run the same Argon2 verify as every other answer; unknown accounts stay locked for `auth.lockout_minutes` like real ones; locking an account ends its sessions (#31, REQ-16, review findings 1, 4, 12d)
- Session gate on every API route: `identity.permissions.authorize` is an app-wide dependency that checks `Origin` on mutating requests (CSRF), requires a live `rw_session` on every route not marked public (deny by default), blocks all but `/auth/me`, `/auth/logout` and `/auth/password` while a temporary password is in force, and enforces each route's `x-permission`; the live OpenAPI document lists the gate's 401 and 403 problem responses; `/api/v1/openapi.json` is no longer served in production (#31, REQ-16)

### Changed
- The live OpenAPI document lists the request size limit's `413` problem on every operation with a body, since a body whose fields are within their limits can still exceed 2 MB once JSON-escaped; this fixes an intermittent Schemathesis failure on `PUT /admin/legal` (#31, REQ-16, BL-64)
- Coverage measurement follows greenlets (`concurrency = ["thread", "greenlet"]`), so lines after SQLAlchemy asyncio calls are counted; combined coverage was under-reported (about 86 percent measured, 96 percent actual at this change) (REQ-25)
- Coverage floors (CP-04, owner decision on BL-72): `make test` and the CI `test-api` job run the unit tests (100 percent floor on security-critical modules) and then the database integration tests against a throwaway PostgreSQL in Docker, with the 85 percent floor on both together; `make test-unit` runs the unit tests alone; tests needing the Compose stack are marked `stack`; 7.1 and `M0-tooling.md` amended (#32, BL-72, REQ-25)
- License allow-list: MIT-0, BlueOak-1.0.0 and Python-2.0 added by owner decision, and the nine tooling exceptions for them removed; data terms TW-OGDL-1.0, BOE-2024 and UrhG-5 added to ADR-0003 decision 5, with the five PRC statute excerpts approved for the private test corpus only; ADR-0003 amendment 2 (#29, #12, BL-59, BL-63, REQ-20, REQ-25)
- License allow-list: PSF-2.0 and SIL OFL-1.1 (fonts only) added by owner decision; ADR-0003 amended (BL-53, BL-57, REQ-20)

### Added
- M2 `AttributeValidator` (`regwatch.taxonomy.validator`) for M3, M4, M5 and M7: checks `item.attributes` per facet type (active term keys, a list only for `multi` facets; one-line-safe text up to 2,000 characters; finite numbers; `YYYY-MM-DD` dates; booleans), optionally requires `required` facets, normalises values, and reports every bad field in one 422 problem; `get_validator` caches a snapshot per process until `taxonomy.version` moves; Hypothesis is now a direct dev dependency for the property test (REQ-03, REQ-11)
- M2 import and export: `GET /taxonomy/export` writes every facet and term as YAML in the seed files' shape with `schema_version: 1` (parents before children), and `POST /taxonomy/import` creates missing facets and terms and updates only the fields given, in one transaction; importing the seed files or an export a second time changes nothing; imports cannot change `system` or a facet's value type, and refuse YAML aliases (REQ-03, REQ-11)
- M2 jurisdictions: `GET` and `POST /jurisdictions` (filters by kind and active), `GET` and `PATCH /jurisdictions/{code}` and `GET /jurisdictions/regions` (the 17 UN M49 sub-regions with their active member codes); codes are checked per kind (ISO 3166-1, ISO 3166-2 under an existing country, or a short upper-case code for supranational bodies) and keep their code and kind; changes are audited (REQ-03, REQ-11)
- M2 merge and rule test: `POST /taxonomy/terms/{id}/merge` moves item tags (keeping the higher confidence), term keys in `item.attributes`, `source.default_term_ids` and child terms to the target, keeps the merged names as synonyms and deletes the merged term; `POST /taxonomy/terms/{id}/test-rules` evaluates match rules on sample text with `regwatch.taxonomy.rules.evaluate`, which M4 reuses (REQ-03, REQ-11)
- M2 terms: `GET` and `POST /taxonomy/facets/{key}/terms` (tree or flat, with item counts, optionally inactive terms), `PATCH` and `DELETE /taxonomy/terms/{id}`; parents must be in the same facet and cycles are refused; synonyms are normalised; match rules are bounded and regexes with nested quantifiers or quantified alternation are refused; a term that items use is deactivated instead of deleted, and children of a deleted term move up; every change is audited and bumps `taxonomy.version` (REQ-03, REQ-11, BL-74)
- M2 facets: `GET`, `POST`, `PATCH` and `DELETE /taxonomy/facets` (system facets can be hidden, not deleted or retyped; facets with tagged items cannot be deleted; keys `country`, `region` and `regulation` are reserved for the built-in view dimensions) and `GET /taxonomy/view-dimensions`; every change is audited and bumps the new `taxonomy.version` setting, which only the taxonomy service writes (REQ-03, REQ-11)
- M1 independent security review record `docs/evidence/phase-1/M1-security-review.md` (6 medium, 5 low, 1 info finding; sign-off pending fixes) and the M1 assumptions in `docs/decisions/ASSUMPTIONS.md` (#31, #32, REQ-16, REQ-25)
- `GET /branding`, `PUT /admin/branding` and `PUT /admin/legal` (stored text; the rendered `/legal` page and the logo upload follow BL-68) (#32, REQ-17, BL-10)
- Runtime settings typed and bounded by the registry, with the 8.4 data-processing-basis rule for a hosted translation provider, and feature flags with the same precondition (#32, REQ-16)
- The registries contract ships in the package as `regwatch/core/registries.yaml`, read by `regwatch.core.registry` (setting definitions, permission keys); a unit test holds it byte-identical to `docs/contracts/registries.yaml` (#32, REQ-16)
- Role administration: create, update and delete with system-role and in-use guards (the admin role keeps every permission) and the permission catalogue; changes audited with before and after values (#32, REQ-16)
- Audit viewer `GET /admin/audit` with actor, action, entity and time filters, newest first, with the actor's email (#32, REQ-16)
- User administration: list with search and status filter, create with a one-time temporary password, update name, roles and status (admin unlock), reset password ending the user's sessions; no change may leave the deployment without an active user holding `users.manage`; role changes apply on the next request (#32, REQ-16)
- `POST /auth/password` (policy from `auth.password_min_length`; ends every other session and rotates the current one) and `GET`/`DELETE /me/sessions` (#31, REQ-14, REQ-16)
- `POST /auth/login` and `POST /auth/logout`: `HttpOnly; Secure; SameSite=Lax` cookie rotated on login, 5 attempts per minute per IP and per account, lockout after `auth.lockout_threshold` failures in 15 minutes for `auth.lockout_minutes` with identical answers for unknown accounts, audit rows for login, failure, lock and logout (#31, REQ-14, REQ-16, BL-50)
- `GET /auth/me`; sessions resolved from the `rw_session` cookie with an idle timeout from the user preference bounded by `sessions.idle_timeout_max_minutes` and an absolute lifetime of `sessions.absolute_lifetime_hours` (#31, REQ-16)
