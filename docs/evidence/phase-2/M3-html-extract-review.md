## Data flows touched
- **Captured body to tree:** a fetched body (bytes, hostile) and the charset label the server sent go to `tree.parse`. html5lib decodes the first 2 MiB (the transport label, else BOM, `<meta>` prescan or windows-1252) and tokenizes it. The capped tree builder then builds an `xml.etree` tree. `Page.root` is the `html` element, and `cut` says whether the body was truncated.
- **Rules to selectors:** holders of `sources.manage` save `content_selectors`, `exclude_selectors`, `title_selector` and `date_selector`. These are compiled at save time (`compile_selector`) and again at run time.
- **Tree and selector to elements:** `Selector.select(root)` walks the tree once per call (`elements`) and returns matches in document order. Text extraction (not in this slice) will read them.
- **Errors:** `ParseError(reason, detail)` has fixed detail text with no page content. `SelectorError` carries the selector text (admin input) and up to 20 characters of it. Any other exception would end a capture run as `internal-error`.
- **Trust boundary:** the body and the charset label are hostile (8.1). Selectors are admin input, checked on save.

## Findings
| # | Severity | Description | Fix PR | Verified |
| --- | --- | --- | --- | --- |
| 1 | high | **The 10 s parse deadline is checked only when an element is pushed, so a hostile page of 2 MiB or less can hold a worker for minutes to about an hour.** `_Stack.append` is the only check (`tree.py:57-58`). html5lib's tokenizer and its etree builder grow strings by `+=` on dict and element attributes, one piece per character or per token, which costs time quadratic in the length (`_tokenizer.py` tag name, attribute name, comment and doctype states; `treebuilders/etree.py:110-130` `insertText`). The duplicate-attribute check scans every earlier attribute of the tag for each new one (`_tokenizer.py:924-930`). None of this pushes an element. The module docstring says "text is linear", but it is not. Measured (`run_one.py`, one core): `b"<p>" + b"< " * 1_048_574` (2 MiB) took **295 s** and returned a page; `b"<p>" + b"& " * ...` (2 MiB) took **288 s** and returned a page; `b"<a" + b"x" * ...` (one 2 MiB tag name) ran **278 s** before the `too-slow` refusal at the first push after the token; `b"<!--" + b"- " * ...` took **163 s** and was then refused. `b"<p " + b"a " * 100_000 + b">"` (200 KB) took **48 s**, and 400 KB took **232 s** before the late `too-slow`. 100 KB of distinct names (`a0 a1 ...`) took 6 s (86 s at 200 KB). These grow at least quadratically, so a 2 MiB tag of attributes would run past the worker's 3,600 s hard limit (`core/worker.py:29-30`). Other quadratic cases at 200 KB: `<select>`, `<svg>`, `<textarea>` and `<script>` bodies of `< ` or `<!--<script>` (3 to 5 s each). Anyone who can publish on a monitored page, comment fields included, can do this on every scheduled run. ADR-0009 decision 5 says parsing runs in a worker thread, which cannot be interrupted from outside. Fix direction: check the deadline inside tokenization, for example by wrapping the tokenizer stream's `char` and `charsUntil` (or the token loop plus a cap on the length of one tag, comment or doctype token, and on attributes per tag). Build text in an element class that collects pieces in a list and joins them once. Alternatively, parse in a child process with a hard timeout and an address-space limit. Add the generators above as tests. | | |
| 2 | low | **Memory is not bounded by the element cap: parse errors, comments and adoption agency clones are not counted.** html5lib keeps every parse error in `parser.errors` (`html5parser.py` `parseError`): 200,000 errors held 43 MiB (tracemalloc), and `b"<p>" + b"< " * ...` at 2 MiB peaked at **262 MiB** RSS. 2 MiB of `<!---->` gives 299,593 comment nodes and 115 MiB with no push. The adoption agency algorithm clones formatting elements into the stack with `insert` and item assignment, not `append`: `(<div><b><i><u><s><em><strong><code><big><p>x</big>...</b></p></div>) * 2000` has 36,003 elements for 20,003 pushes (1.8×). A late `<meta charset>` makes html5lib reparse with a new `_Stack`, so the count restarts: `<br>` × 150,000 then `<meta charset=koi8-r>` gave 300,010 pushes and a page. Bounded (a few hundred MiB per parse), but the `_Stack` docstring ("this also counts elements") and ADR-0009 decision 5 ("cannot exhaust memory") claim more. Fix direction: a parser subclass whose `parseError` does not store errors, counting comments with elements, counting in `insertElement` and `cloneNode` rather than `append`, and keeping the count (and deadline) across the reparse. | | |
| 3 | low | **Selector matching has no time bound, and each `select` call walks the whole tree again.** On a 2 MiB page of 174,769 elements, with one core and no other load: `p` took 0.47 s, 8 steps of `*` took 1.18 s, and `",".join([" ".join(["*"] * 8)] * 10)` (159 characters, within every limit) took **8.4 s**. The saved rules allow up to 20 content selectors as well as exclude, title and date selectors (`MAX_SELECTORS = 20`, in the uncommitted `config.py`), so ordinary selectors cost about 0.5 s each on such a page and pathological ones can cost minutes per page. The admin chooses the selectors, but the page chooses the element count. Fix direction: walk once per page and share it between selectors (`elements` is pure), bound the total number of steps across a rule, and check a deadline in `select`. | | |
| 4 | low | **Some matches differ from a browser's, so selectors copied from developer tools can match more or less.** (a) Class and `~=` matching uses `str.split()`, which splits on Unicode and ASCII separator characters that CSS does not treat as whitespace: with `class` set to `a\u00a0b`, `a\u2003b`, `a\x1cb`, `a\x85b` or `a\u3000b` (UTF-8), both `.a` and `[class~=b]` match, but a browser matches neither (`select.py:159`, `178`). Split on `[ \t\n\f\r]` only. (b) html5lib keeps a namespace on SVG and MathML elements (`{http://www.w3.org/2000/svg}svg`), so `svg`, `rect`, `math` and `svg > *` match nothing. The `Page` comment ("without a namespace", `tree.py:73`) is wrong for foreign content. SVG attribute names keep their case (`viewBox`), but selector names are lowered, so `[viewBox]` never matches. (c) `<template>` contents are ordinary children in html5lib's etree, so `template p` matches inert, unrendered content, though `querySelector` does not find it. | | |

## Checked and found fine
- **Depth and push caps:** `reset` replaces `openElements` after `super().reset()`, and html5lib never assigns `openElements` anywhere else. Every `insertElement` path (normal, table and foster parenting, reconstruction) goes through `append`. `<div>` × 100,000 and `<b>` × 100,000 are refused as `too-deep` in 0.02 s, and 2 MiB of `<br>` is refused as `too-large` in 1.1 s at 137 MiB. Every adoption agency pattern tried that nests is refused as `too-deep` within 0.1 s. The 2 MiB cut is applied to the bytes before decoding, and `cut` is reported.
- **Exceptions:** `ParseError` raised inside html5lib is not caught by html5lib (only `_ReparseException` is), so it reaches the caller. Across 26 labels (unknown, empty, NUL, `replacement`, `utf-7`, `utf-16`, `x-user-defined`, ISO-2022 and others) × 40 bodies (BOMs, late and odd `<meta charset>`, surrogate and out-of-range character references, foreign content, `<template>`, `<frameset>`, `<plaintext>`, NUL bytes), and 20,000 random tag-soup bodies, nothing raised other than `ParseError`, apart from the surrogate label (finding 6d). Unknown labels fall back to sniffing.
- **Walk:** `elements` is iterative, skips comments and processing instructions (function tags), and numbers element children only, so `:first-child`, `:last-child` and `:nth-child` ignore comments and text, as in CSS. The root is `html`, and the doctype and comments outside it are not in the tree.
- **Selector compile cost:** with a 300-character limit, the worst cases tried (unclosed `:nth-child(`, `[`, `:not(`, long names, quoted values, `.a` × 150, `*` × 300, digit runs) compile in under 0.07 ms. `_TOKEN` and `_NTH` have no nested quantifiers that could backtrack exponentially, and `int` on up to 288 digits is far below Python's 4,300-digit limit.
- **Selector compile checks:** 100,000 random selectors raised only `SelectorError`. A leading or trailing combinator, a trailing comma, an empty `:not()`, nested `:not`, a combinator inside `:not`, `|=`, `+`, `~`, pseudo-elements, more than 10 alternatives or 8 steps, and non-strings are all refused. A type selector after a class is refused. Tag and attribute names are lowered, which is right for HTML elements.
- **An+B arithmetic:** `_nth` is right for a = 0 (index = b), negative a (`-n+3` gives 1 to 3, `-2n+5` gives 1, 3, 5), negative b (`3n-2` gives 1, 4, 7; `-n-1` gives none), `0n+0` (none) and `n+0` (all). Python's floor division and modulo with a negative a give the right sign test, and large a or b only make the set empty.
- **Attribute operators:** `[a=""]` matches an empty value. `[a~=""]`, `[a^=""]`, `[a$=""]` and `[a*=""]` match nothing, as Selectors 4 says. `~=` with a space in the value matches nothing. `#a#b` needs both. An id matches the whole value.
- **Matching algorithm:** for step i, the child combinator reads the parent's own bits, and the descendant combinator reads the bits of the parent and its ancestors, so the result is the same as right-to-left matching, with no backtracking (checked on `div:not(#main) p`, `* > section *`, `body > p` after foster parenting, and `table > tr`, which is empty because `tbody` is implied). `id()` keys are stable because `walk` keeps every element alive. Results are de-duplicated across alternatives and returned in document order.
- **Dependency records:** pins `html5lib>=1.1,<2` and `webencodings>=0.5.1,<0.6`, with exact versions and sha256 hashes in `uv.lock`. Both are pure Python (`py2.py3-none-any`), with no native code. six 1.17.0 is already C15. The register's former trafilatura and readability-lxml rows are kept, marked "not used". The `webencodings` exception has `scope = "any"` and BSD-3-Clause, which is on the allow-list, and it is used by the scan (no "unused" warning). html5lib's wheel ships its LICENSE and AUTHORS.
