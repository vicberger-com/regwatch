## Data flows touched
- **Worker to source hosts:** feed, pages and robots.txt through CaptureFetcher and SafeFetcher. The `User-Agent` is built from `capture.user_agent` and `general.contact_email`. The body cap comes from `capture.max_body_bytes`.
- **Worker to Valkey:** per-host rate slots (`regwatch:rate:*`) and `LLEN capture` from the tick.
- **Worker to the object store:** raw bodies under `raw/{source_id}/{sha256}` and the manifest under `raw/{source_id}/runs/{run_id}.json`.
- **Worker to PostgreSQL:** the run row (status, counts, `bytes_fetched`, `robots_decision`, `error_class`, `error_message`), `capture_job.last_run_at`, `source.health` and `consecutive_failures`.
- **Trust boundary:** everything a source host sends (status lines, headers, bodies, robots.txt, Crawl-delay) and admin-set settings.

## Checklist
- [x] Input validation: job settings are re-validated at run time (`bad-config`). `max_items` counts failures too. The override reason is passed only with `robots_policy=override`.
- [ ] Limits: `capture.max_body_bytes` has no bounds (finding 8), and no time budget fits a run to the worker's time limit (finding 1).
- [ ] Error text never quotes content: URLs are cleaned, but httpx and h11 exception text is passed through (finding 6).
- [x] Outbound requests only through SafeFetcher: connectors get only `ctx.fetcher` (a CaptureFetcher). The tests reach no non-loopback address (`netguard.py`: 0 attempts in both files).
- [x] Resources closed: one `httpx.AsyncClient` per fetch, closed by `async with`; the Valkey client is closed in `finally` in `_run` and `_tick` (tested); the engine is disposed per task.
- [ ] Outcomes and health correct in all paths (findings 1, 2, 3, 5, 7).

| 1 | high | **No time budget: settings the API accepts produce runs that the worker kills, and these runs never end or count.** `run_connector` (`execution.py:124-133`) fetches every candidate in sequence. Each fetch waits for its rate slot: `interval(rate, crawl_delay)`, up to `MAX_WAIT_S` = 120 s before it is refused (`capture.py:22,61`). The job schema allows `rate_limit_per_minute` from 1 and `max_items_per_run` up to 2000 (`schemas.py:47-48`); RSS `max_entries` defaults to 100 and goes up to 1000 (`config.py:37`). The worker's soft limit is 3300 s and its hard limit 3600 s (`worker.py:29-30`). Its comment assumes "200 pages at 30 a minute". **Failure case (arithmetic, not run against a real worker):** with a rate of 1 per minute, or a site Crawl-delay of 60 s, the default 100 entries need about 100 minutes; 1000 entries at 30 per minute need 33 minutes, and 2000 need 67. At the soft limit, `SoftTimeLimitExceeded` passes through `run_connector` and `execute`, which catch neither, so the transaction rolls back and the run stays unfinished. Its stored bodies have no manifest. The tick hands the run over after 10 minutes, so the hour of work is repeated. The sweep then ends it as `abandoned`, which is in `NOT_THE_SOURCE`, so the source keeps its old health (for example `healthy`) and has no `error_message`. The job's next scheduled runs wait behind the unfinished run. Throughout, the worker holds a PostgreSQL transaction open for up to 55 minutes (BL-90 (c)), which also holds back vacuum. **Fix:** give `run_connector` a deadline well under `SOFT_TIME_LIMIT_S` (for example `anyio.move_on_after(40 * 60)` around discovery and fetching). When it passes, stop and end the run as `partial` (or `failed` with nothing fetched) with error class `time-budget`, keeping the documents fetched so far and writing the manifest. Also refuse, at job save, settings whose minimum duration (`max_items * 60 / rate`) exceeds the budget. In `execute`, catch `SoftTimeLimitExceeded` and close the run. | | |
| 2 | medium | **Unexpected exceptions leave the run unfinished, silent and outside health.** `run_connector` catches only `FetchRefusedError` and `ConnectorError` (`execution.py:132-139`), and `execute` (`runs.py:285-289`) catches nothing. **Failure cases:** <br>• `outcomes.py`, case "store fails": an `OSError` from the store propagates out of `run_connector`. <br>• The same happens on every run with an S3 endpoint configured (`objectstore.py:30-31` raises `ObjectStoreError`). <br>• It happens on any Valkey error inside `ValkeyRateLimiter.take` (`rate.py:81`), or on a `MemoryError` (see 8). <br>In each case the transaction rolls back, the run is handed over up to 3 times and each attempt fails again, and the run ends as `abandoned`. `source.health` never moves, so a source that cannot be captured at all shows as healthy. **Fix:** in `execute`, catch `Exception` around `run_connector`, log the traceback (to logs only) and close the run as `failed` with a constant message. Use an error class that says whose fault it is: `store-unavailable` or `queue-unavailable` for our own failures (left out of health, like `NOT_THE_SOURCE`), and `internal` otherwise. Add a test with a raising store. | | |
| 3 | medium | **Refusals during document fetches count as source failures, so robots.txt disallowing the page paths fails the run instead of skipping it.** In the per-candidate loop, every `FetchRefusedError` and `ConnectorError` adds to `failures` (`execution.py:132-133`). With no document, the run is `failed`/`fetch-failed` (`execution.py:143-145`) and degrades the source. **Failure cases** (`outcomes.py`): <br>• robots.txt `Disallow: /p/`, with the feed allowed and both entries under `/p/`, gives `status=failed class=fetch-failed decision=None`. <br>• `Crawl-delay: 300` gives the same: the second slot is more than 120 s away, so every page is refused as `rate-limited`. <br>Five such runs make the source `unhealthy`. Acceptance 4 says "a site disallowing the path in robots.txt is skipped with status `skipped` and reason recorded", and ASSUMPTIONS treats a busy host as `skipped`. In a mixed run, `robots_decision` reads `allowed` even when pages were disallowed. After the first `rate-limited` refusal, the remaining candidates are each refused the same way, and none of these refusals is reported. **Fix:** classify per-document refusals. A `robots` refusal skips that document and is counted apart from failures; when every document is disallowed, end as `skipped` with `disallowed`, and record that some pages were disallowed when only part were. On `rate-limited`, stop the run and end it as `partial` (or `skipped` when nothing was fetched) without consuming the rest. Count only errors that are the source's (timeouts and connection failures after retries, HTTP errors) toward `failed`. Add the two cases above as tests. | | |
| 4 | medium | **The manifest drops what M4 needs to make items.** `_manifest` (`execution.py:94-100`) writes `url`, `final_url`, `status`, `body_ref`, `mime`, `fetched_at` and `text`. The candidate's `title`, `published_at`, `external_id` and `language` are not in `RawDocument` (`rss.py` `fetch` sets no `metadata`), so they are lost after the run. **Failure case** (`outcomes.py`, "allowed"): an entry with a `<title>` and `<pubDate>` appears in the manifest with neither, although ASSUMPTIONS says M4 makes items from the manifest. **Fix:** carry the candidate's fields into the manifest row (or into `RawDocument.metadata` from the connector). They are already plain text and capped. Test that a feed's title and date reach the manifest. **Info, same row:** `final_url` keeps the query of redirect targets, which can carry signed tokens; if M4 does not need it, store only the origin and path. | | |
| 5 | low | **`bytes_fetched` counts what was stored, including the manifest, not what was fetched.** `counting_store` wraps `ctx.store` (`execution.py:116-121`), and the manifest itself goes through it (`execution.py:141-142`). **Failure case** (`outcomes.py`, "allowed"): `bytes=689`, of which 667 are the manifest and 22 the two pages; the 267-byte feed is not counted. With `fetch_full_page` off, only the summary text is counted. Failed and skipped runs record 0 even when the feed was fetched. The unit test enforces this behaviour (`test_capture_execution.py:105`). **Fix:** count the body sizes in the fetcher passed to the connector (wrap `CaptureFetcher.fetch`), including the feed and failed attempts, and leave the manifest out. Fill `http_status` from the starting fetch while there. | | |
| 6 | low | **`error_message` can quote bytes the server chose.** `_hop` maps every `httpx.HTTPError` to `FetchRefusedError("connect", f"{target.host}: {exc}")` (`fetch.py:273-274`), and h11 puts the offending line in its message (`h11/_readers.py:68,104` via `validate`). When this happens during discovery, `execution.py:137` stores it. **Failure case** (`h11_quote.py`): a server answering with the header line `bad header line no colon` produces `error_message` `feeds.example: illegal header line: bytearray(b'bad header line no colon')`. A hostile host can write up to about 500 characters of its own text into a record that admins and editors read. This contradicts BL-90 (h) ("connector messages never quote content") and `schema.sql:149`. `clean_error` makes the text printable and cuts URLs, but does not stop this. **Fix:** in `_hop`, map exception types to constant text, for example "the server's answer was not valid HTTP" for `RemoteProtocolError`, "the connection failed" for `ConnectError`, and "the certificate could not be verified" for SSL errors. Never format `exc`. Test with this listener. | | |
| 7 | low | **`robots_decision` mixes decisions with other things.** `SKIPPING` writes `rate-limited` into `robots_decision` (`execution.py:50,136`), although a busy host is not a robots.txt decision; `error_class` already says `rate-limited`. A robots.txt that could not be read (5xx, 429, timeout: `robots.py` `_fetch`) is recorded as `disallowed`. A run that fetched the feed and then failed records `None` (`execution.py:143-145`). A run with some pages disallowed records `allowed` (see 3). **Fix:** keep `robots_decision` to `allowed`, `disallowed`, `overridden` (and perhaps `unavailable` for a robots.txt that could not be read); set it whenever robots.txt was consulted, whatever the status. | | |
| 8 | low | **`capture.max_body_bytes` has no bounds.** `context_factory` uses `int(settings["capture.max_body_bytes"])` as given (`tasks.py:95`); the settings API checks only that it is an integer (`admin/services.py:95-96`). **Failure cases:** 0 or a negative value refuses every page as `too-large`, which is not retried, so every run fails and every source turns unhealthy. A value in the gigabytes lets one page grow to the 4 GiB address-space cap, where `MemoryError` takes finding 2's path. **Fix:** a range in the registry (for example 64 KiB to 100 MiB), enforced at save and clamped in `context_factory`. | | |
| 9 | low | **Some permanent failures are retried as transient.** `connect` covers every `httpx.HTTPError` (`fetch.py:273-274`), including certificate verification failures (raised by httpx as `ConnectError`) and `RemoteProtocolError`. These are retried 3 times with back-off (`execution.py:49,80-87`), and each attempt takes a rate slot. A failed certificate check is a refusal by policy. **Fix:** give TLS verification and protocol errors their own non-transient reasons (`tls`, `protocol`). Keep `connect` and `timeout` for connection setup, reset and read failures. | | |
| 10 | low | **The process-wide robots caches grow with every user agent.** `_robots.setdefault(agent, ...)` (`tasks.py:34,97`) is never pruned. Each `RobotsPolicy` may hold `CACHE_BUDGET` (4 MiB of robots.txt, "about 100 MB once parsed", `robots.py`). Each admin change of `capture.user_agent` or `general.contact_email` adds one per worker process until the process is recycled. This is admin-driven and bounded by the 1 GiB recycle and 4 GiB cap. **Fix:** keep one entry, and replace it when the agent differs. | | |
| 11 | low | **The tick's backlog check sees only messages no worker has taken.** `LLEN capture` (`tasks.py:120-121`, used at `runs.py:195`) does not count messages a worker has already received. That includes every run sent with a countdown (the tick's jitter): the worker holds it until its ETA, unacknowledged because of `task_acks_late`. It also includes one prefetched message per process. A run that waits more than 10 minutes in a worker is therefore handed over again, and the extra hand-over uses up one of the `MAX_HANDOVERS`; the duplicate message finds nothing to claim, or claims the job's next run early. Conversely, a queue that never drains blocks every hand-over, so lost runs wait for the 2-hour sweep. The check is awaited while the tick holds its job row locks (up to the 5 s socket timeout), and a Valkey error now aborts the whole tick; this is harmless, since publishing would fail too. **Fix:** acceptable for now; document the limits in `runs.py`. A sharper check would also count the transport's `unacked` entries for the `capture` queue, or hand over only runs older than the longest countdown plus `HANDOVER_AFTER`. | | |

| 13 | info | **An admin can set any user agent.** robots.txt groups are matched for the fixed token `regwatch` (`robots.py` `PRODUCT`), so an agent string claiming to be a browser or another crawler gets past User-Agent filters while robots.txt is still applied as for `regwatch`. Header injection is not possible (see "Checked and found fine"). **Fix:** if wanted, require the agent to start with `regwatch/`. | | |

## Checked and found fine
- **Retries:** each document is fetched at most `MAX_ATTEMPTS` = 3 times (`stop_after_attempt(3)`, `reraise=True`; unit test counts 3 calls, never 4). Only `FetchRefusedError` with reason `timeout` or `connect` is retried. `private-address`, `robots`, `rate-limited`, `too-large`, `ConnectorError` (HTTP status) and others are not. Discovery is not retried, as ASSUMPTIONS says. The back-off is 1 s, then 2 s. Each attempt takes its own rate slot.
- **Override:** `job_settings` passes `override_reason` only when `robots_policy == "override"` (`execution.py:74`). `check_robots` also clears the reason when the policy is not `override` and refuses a blank one (`capture/services.py:177-184`), so `RobotsPolicy.check`'s `ValueError` for a blank reason cannot be reached from stored data.
- **User agent and settings:** control characters are refused at save for single-line string settings (`admin/services.py:134-142`), and `general.contact_email` passes `check_email`. `user_agent` keeps printable ASCII only, collapses white space and caps 200 characters, so no CR or LF reaches the header (unit test). `{contact_email}` inserted after `{version}` cannot re-expand placeholders.
- **`clean_error`:** user name, password, path and query of `scheme://...` URLs are removed before the 500-character cut. Malformed URLs become `<url>`. Constants from `run_connector` (`N of M documents failed`) quote nothing.
- **Outcomes:** all fetched gives `success`; some fetched gives `partial`/`some-failed`; none fetched gives `failed`/`fetch-failed`; robots.txt disallowing the feed gives `skipped`/`disallowed`, and health is unchanged (integration test, `unknown`). An empty feed gives `success`, 0 items, `healthy`, and no manifest; that is acceptable, though M4 must allow for a missing manifest. `max_items` counts failures too, and RSS also slices its entries to the limit.
- **Resources:** SafeFetcher opens and closes one client per fetch without keep-alive. The robots cache is one per worker process and agent, shared across runs, as intended (but see 10). The run's row lock is taken before its source's in `_close`, which keeps the documented lock order.
- **Manifest key:** `raw/{uuid}/runs/{uuid}.json` passes `objectstore._KEY`, and cannot collide with body keys (64 hex characters, no `/`).

**Not signed off.** The reasons:
- **Finding 1 (high):** job settings the API accepts make runs exceed the worker's time limit. These runs end without outcome, manifest or health change, and hold a database transaction for most of an hour.
- **Findings 2 and 3 (medium):** unexpected errors are invisible to health, and robots.txt or Crawl-delay refusals of pages fail and eventually flag sources, contrary to acceptance 4.
- **Finding 4 (medium):** the manifest M4 depends on drops titles and dates.

Findings 5 to 11 and 14 are low and can be fixed in the same follow-up or tracked in BL-90. Findings 12 and 13 are information only. I will re-verify on a fix commit. · M3 run-connectors independent review · 2026-11-17
