## Data flows touched
- **Worker to www.federalregister.gov:** `discover` fetches `documents.json` with the job's `params` as its query, then each `next_page_url`, through `ctx.fetcher` (CaptureFetcher, then SafeFetcher). Redirects are followed by SafeFetcher, to `unblock.federalregister.gov` too.
- **API JSON to candidates:** `url` (from `html_url`), `title`, `summary` (`abstract`), `external_id` (`document_number`), `published_at`, and `hints["record"]` go to the object store and on to M4, users' browsers, emails and exports.
- **Worker to the object store:** `raw/{source_id}/{sha256}.json` holds the record; the run manifest `raw/{source_id}/runs/{run_id}.json` lists the run's documents.
- **Job to query:** `capture_job.last_run_at` fills the `{last_success_date - N days}` placeholder.
- **Errors:** `ConnectorError(reason, detail)` goes to `capture_run.error_class` and `error_message`, which `sources.read` holders can see; the sources screen shows the new reasons.
- **Trust boundary:** the API's body, status and headers, and anything it redirects to, are hostile (8.1). `source.config` is written by holders of `sources.manage`.

## Findings
| # | Severity | Description | Fix PR | Verified |
| --- | --- | --- | --- | --- |
| 1 | high | **The `{last_success_date - N days}` placeholder uses the last run, whatever its outcome, so documents are missed after failures.** `query` (`api_feed.py:105-109`) fills the date from `job.last_run_at` (`execution.py:101`). `_close` sets `last_run_at = now` for **every** ended run: failed, skipped, `blocked-by-provider`, `partial` and `run-deadline` (`runs.py:117`). It is also the run's end time, not its start. **Failure case:** the starter source (`N = 3`, weekdays) is blocked by the firewall from Monday to Friday. Each blocked run sets `last_run_at`. On the next Monday the window starts on Friday less 3 days, i.e. Tuesday, so Monday's documents are never requested. Any outage longer than N days loses documents silently in the same way, and so does any truncated run (findings 2 and 3). The test `test_the_query_fills_the_last_success_placeholder_and_checks_types` passes a date straight to `query`, so it cannot see this; the ASSUMPTIONS row records "the job's last run time", which contradicts the placeholder's name and R-06's intent. **Fix:** pass the `started_at` of the job's last run with status `success` (a query on `capture_run` in `job_settings`, or a `last_success_at` column set in `_close` only for `success`) as `JobSettings.last_success_at`, keep the 30-day fallback when there is none, correct the ASSUMPTIONS row, and add a test that a failed or skipped run does not move the window. | | |
| 2 | medium | **The page cap and `max_items` cut a run short silently, and the cut documents are never fetched.** After `MAX_PAGES` pages the loop ends without checking whether `next_page_url` is still offered (`api_feed.py:161-192`); `run_connector` also stops at `max_items` (`execution.py:172`). Both end as `success`. With `order: newest`, what is cut is the oldest part of the window, and the next run's window (finding 1) starts later. **Failure case** (`probe.py` 3): 15 pages offered, 10 read, 10 candidates, no error and no signal. With the default `per_page` of 20 that is 200 documents; with the 30-day first run a broad term query exceeds it. **Fix:** when a next page is still offered after the last page read, end the run as `partial` with a fixed reason (for example a `ConnectorError("truncated", ...)` that `run_connector` maps to `partial` after writing the manifest), and do not advance the window (finding 1). Test with distinct next URLs. | | |
| 3 | medium | **A failure on a later page throws away the documents already fetched.** `discover` yields page 1's candidates, which `run_connector` fetches and stores, and then raises `ConnectorError` on page 2 (an HTTP 500, a malformed answer, a next page on another host, a block). `run_connector` returns `failed` from its `except ConnectorError` branch (`execution.py:197-199`) without writing the manifest, so M4 never learns of the stored documents, and `items_new` is 0. RSS never yields before it can fail, so this is new with paging. **Failure case** (`midpage.py`): page 2 answers 500; outcome `failed http-status`, `items_new 0`, 2 objects stored, no manifest. With finding 1 the window still moves on. **Fix:** in `run_connector`, when `entries` is not empty, write the manifest and return `partial` with the connector's reason; or let the adapter stop paging and report the cut as in finding 2. Test it. | | |
| 4 | medium | **Links in the stored record are not checked links, and the candidate link may name any host.** `_record` (`api_feed.py:128-141`) passes `html_url` and `pdf_url` through `plain_text` only. `plain_text` removes tags and decodes entities; it does not check a URL. Only the candidate's `url` passes `entry_link` (`api_feed.py:176`), and `entry_link` accepts any public host. **Failure cases** (`probe.py` 1): `pdf_url: "javascript:alert(1)"` and `pdf_url: "http://169.254.169.254/latest/meta-data"` are stored in the record and in `hints["record"]`; `html_url: "https://evil.example/x"` becomes the candidate URL, the link readers follow for an "official" Federal Register document. Anything later that renders `record.pdf_url` as a link (M4, M6, emails, exports) inherits a script URL or an internal address. **Fix:** pass `html_url` and `pdf_url` through `entry_link`, keep its rebuilt value in the record (drop the field when it returns `None`), and accept only the provider's hosts: `www.federalregister.gov` for `html_url`, `www.govinfo.gov` and `www.federalregister.gov` for `pdf_url`. Test each case. | | |
| 5 | medium | **The block is detected only after the CAPTCHA host has been contacted, and some blocks are not recognised.** SafeFetcher follows the 302, so CaptureFetcher fetches `https://unblock.federalregister.gov/robots.txt` and then the CAPTCHA page before `_blocked` (`api_feed.py:114-116`) looks at the final URL. **Failure cases** (`probe.py` 4, 4b, 5): (a) if the unblock host's robots.txt answers 5xx or cannot be fetched, `RobotsPolicy` disallows, the fetch raises `FetchRefusedError("robots")`, and the run ends `skipped` with `robots_decision` `disallowed`. That is not `blocked-by-provider` and does not count against the source's health (`runs.py:118`), so a lasting block never makes the source `unhealthy`. (b) Every blocked run sends two requests to the CAPTCHA host. (c) An AWS WAF `block` answer (403) or a `captcha` answer (405) with `x-amzn-waf-action` gives `http-status`, not `blocked-by-provider`. (d) Only the final URL is checked, so a chain that passes through the unblock host and ends elsewhere is not a block. Nothing is retried within a run (`discover` is not retried and the next run comes only from the schedule), which is correct. **Fix:** stop at the redirect: give `CaptureFetcher.fetch` a way to refuse a hop (for example a `stop_hosts` set, or a `before_hop` the caller can extend) so a hop to `unblock.federalregister.gov` raises before any request, and map it to `blocked-by-provider`. Check `got.redirects` as well as `got.url`, and treat any status with `x-amzn-waf-action` as a block. Test (a) to (c) and assert the requests made. | | |
| 6 | medium | **JSON answers have no size cap of their own and are parsed on the event loop.** `parse_json` (`api_feed.py:81-89`) runs `json.loads` and `_depth` on whatever the fetcher returns, i.e. up to `capture.max_body_bytes` (10 MiB by default, up to 50 MiB), synchronously inside `async discover` (`api_feed.py:169`), for each of up to 10 pages. The RSS connector, for the same reason, caps feeds at 5 MiB and parses in a thread (RSS finding 3 and its re-verification). **Measured** (`jsontime.py`, `[{}, {}, ...]`): 10 MiB took 1.5 s at 354 MiB peak RSS; 50 MiB took 7.9 s at 1.6 GB, under the 4 GiB address-space cap only by a margin. The depth limit itself works: deep bodies raise `RecursionError` in `json.loads` or are refused by `_depth`, and huge integers raise `ValueError`; both give `malformed-answer`. **Fix:** refuse answers over a connector cap (for example 5 MiB, ample for `per_page=1000` with `fields[]`) as `too-large` before parsing, through `ctx.fetcher` limits or a length check; parse with `anyio.to_thread.run_sync`. Test a body just over the cap. | | |
| 7 | medium | **The R-06 starter configuration fails every run, and `params` are checked only when the job runs.** `query` refuses anything but strings and lists of strings (`api_feed.py:101`). The starter source in R-06 section 4 has `per_page: 100`, an integer, so every run fails as `bad-config` (`probe.py` 2: "query parameter 'per_page' is not a short text"). `validate_config` (`config.py`) accepts `params` as `dict[str, Any]`, so the source saves cleanly and the admin learns of the problem only from the first run. connectors.yaml says params are "validated by the adapter", which should happen on write. **Fix:** accept integers (not booleans) and format them with `str`; run the adapter's parameter check from `validate_config` (or a `field_validator` on `ApiFeedConfig` keyed by provider) so a bad value is a 422 on save. Add the R-06 starter config as a test fixture. | | |
| 8 | low | **Query bounds are incomplete.** (a) `MAX_PARAMS` counts keys, but a list value has no length limit: `{"k": ["a"] * 100000}` builds a 400 KB query string (`probe.py` 7) before SafeFetcher refuses the URL. (c) `page` is accepted (`page=100`), which brings back the silent page-1 answer of E-FR-8. (d) A malformed placeholder (`{last_success_date}`) is sent literally (`probe.py` 8), and nothing requires a `conditions[publication_date][gte]` bound, which R-06 asks for on every run. (e) `endpoint_url` is ignored for `federal_register` without a word. The host and path cannot be changed: `urlencode` percent-encodes `?`, `#`, `/` and `@` in keys and values, and the endpoint is a constant. **Fix:** cap the number of values and the encoded query length (for example 1,500 characters) with `bad-config`; refuse `page`, any value containing `{last_success_date` that does not match, and `endpoint_url` for this provider; require the date bound or document why not. | | |
| 9 | low | **`next_page_url` may point at any path on the origin, and a loop is not noticed.** Only scheme and netloc are compared (`api_feed.py:186-192`). **Failure case** (`probe.py` 6): `next_page_url: https://www.federalregister.gov/documents/full_text/text/x.txt` is followed, and a next URL equal to the current one is fetched again until the cap. ## Checked and found fine
- **Endpoint and host:** the endpoint is the constant `FEDERAL_REGISTER`; `source.url` and `endpoint_url` are not used. `urlencode` percent-encodes every reserved character in keys and values, so no `params` entry can change the scheme, host, path or fragment.
- **Same origin:** `(scheme, netloc)` is compared exactly, so userinfo (`https://u@www.federalregister.gov`), an explicit port or another case are refused (strict, never permissive). SafeFetcher checks every hop's address anyway.
- **Paging by `next_page_url` only:** no page number is computed; the loop is bounded by `MAX_PAGES`.
- **No retry around a block:** `run_connector` retries only `connector.fetch`, which makes no network request for this connector; `discover` is never retried.
- **Header case:** `FetchResult.headers` comes from httpx with lower-case names, so `X-Amzn-Waf-Action` is found (`probe.py` 5b).
- **Text values:** `title`, `abstract`, `type`, dates and agency names go through `plain_text` (repeated cleaning, controls removed, length caps); unknown fields are dropped; non-string values are left out; agencies are capped at 20.
- **JSON depth:** `_depth` stops at 33 levels; `json.loads` raises `RecursionError` on very deep bodies and `ValueError` on integers over 4,300 digits, and both are `malformed-answer`.
- **Errors:** every `ConnectorError` detail is a constant, an integer status, or the first 50 characters of an admin-written key. `FetchRefusedError` details are replaced by fixed text in `_refusal`, and `clean_error` cleans what is stored.
- **Storage:** the key is `raw/{source_id}/{sha256}.json` with `source_id` from the job row; the record is `json.dumps` of cleaned values, so equal records share an object and nothing from the API shapes the key.
- **Other providers:** `eur_lex`, `legislation_gov_uk` and `generic_json` fail at once as `not-implemented`, before any request.
- **Dev secrets, queue password:** `dev-env.sh` writes 24 random bytes as hex, `queue.env` with mode 600, and changes only the `REGWATCH_QUEUE_URL` line on upgrade; the test checks these.
