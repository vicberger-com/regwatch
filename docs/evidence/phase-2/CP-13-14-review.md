## Data flows touched
- **Worker to PostgreSQL:** `capture_job.cursor` written in `_close` after `success` and `partial` runs. **Admin to API:** `PATCH /sources/{id}` clears it when `config` changes.
- **Worker to the Federal Register:** the query's lower bound comes from the cursor (less N days), and `order=oldest` is forced.
- **Admin to API:** `POST /sources/{id}/test` (gate `sources.manage`) writes an audit row, counts the request in Valkey, publishes `capture.dry_run(source_id, request_id)` and polls `regwatch:dry-run:{request_id}` for up to 30 s.

## Checked and found fine
- **The cursor only moves forward:** `_cursor` returns None unless the newest stored date is strictly later than the stored one, and `_close` saves it only for `success` and `partial`. Only one unfinished run per job exists (`uq_capture_run_unfinished`), so two runs cannot race on it.
- **Busy dates and the overlap:** the bound is `gte` on a whole US Eastern date (`_cursor_time` at midnight Eastern, less N days, back to a date). A run cut short in the middle of date D restarts at D − N, so the rest of D is read again, never skipped. With N = 0, the bound is D itself. `_published` (midnight UTC) and `.date()` give the same D.
- **Cursor and last success:** order is cursor, then last success, then 30 days back. After a reset the job falls back to its last success, the safe direction. Failed, skipped and blocked runs carry no cursor, because `run_connector` returns before `_cursor` or stores no entries.
- **The reset:** it compares the validated, stored-form `config` before and after, so a rename keeps the cursor and a new feed or params clears it (integration test).
- **API stays offline:** `test_source` calls only `dryrun.request` with `tasks.publish_dry_run` and a Valkey client. `preview` and `run_on_worker` run only in `capture.dry_run`.
- **Request id and key:** the key comes from `uuid.uuid4()` on the server, never from the client. Only the request that made it polls it, and the API deletes it on read. The worker writes it with a 120 s TTL, so the answer to a request that timed out expires.
- **Nothing stored or recorded by the worker:** `_no_store` replaces the object store. No `capture_run`, health, `last_run_at` or cursor is written. Rows are detached and the transaction is rolled back before any fetch, and the task's engine uses `NullPool`, so no connection is held while fetching. Robots.txt and per-host rate limits apply as for runs.
- **Markup:** `TestResult` renders titles, URLs and warnings as React text, and URLs are `<code>`, not links. Titles are already plain text (`plain_text`), and FR links are limited to `FR_LINK_HOSTS`.
- **Audit and permission:** `source.test` with actor, IP and request id is committed before publishing, so 503 and 504 attempts are audited too. `authorize` enforces `x-permission: sources.manage`. A viewer gets 403, and a reader sees no Test button.
- **Registries:** the `capture.dry_run` row is identical in `docs/contracts/registries.yaml`, `api/seed/registries.yaml` and `api/src/regwatch/core/registries.yaml`.
