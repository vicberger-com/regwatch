| 1 | low | `api/src/regwatch/identity/services.py:115-119`, used at `:194-196` and `:425` | **A refund removes the newest hit in the window, not the hit this attempt added.** `refund` pops the last timestamp without pruning or identifying its own entry. (a) If a successful sign-in takes longer than the 60 s window (database pool wait, row-lock queue, slow Argon2 under load), its own hit has already expired and the refund deletes someone else's failure: proof of concept, 29 live failures on an address, one success finishing 60.5 s after it started, count 29 to 28. (b) Otherwise the refund swaps a fresh failure for the older success timestamp, so that failure stops counting early: a failure 50 s into a success that ends 5 s later is forgotten after 5 s instead of 55 s. An attacker holding one valid account behind the same address can use slow or overlapping successful sign-ins to trim the per-address count while spraying other accounts. The gain is bounded by request latency, so practical impact is small, but it contradicts "only success is refunded". | Have `hit()` return the timestamp it appended and pass it back; `refund(key, ts)` removes exactly that value if it is still present (`deque.remove` in a `try`), and does nothing otherwise. Same for `password_changes`. Add a unit test with a patched clock for both cases. |
| 2 | low | `api/src/regwatch/identity/services.py:414-427` and `:453-462` | **Authenticated Argon2 work is now unthrottled.** A correct password is refunded on both routes, and in `change_password` the refund happens right after the current password verifies, before the new-password policy checks (`:469-477`). Scenario: one compromised or malicious low-privilege account drives sustained Argon2 load from one address and grows the session table, which a per-failure limit cannot stop. | Keep "only failures count" for the user-visible limits and add a generous ceiling on all attempts: for example 30 per minute per account for sign-in and 10 per minute per user for password changes, counting successes and policy failures, not refunded. ## Checked and found fine
1. **Every failure path in `login()` is counted and only success is refunded.** The attempt is counted at `services.py:377` before any `await`; `forgive_login` runs only at `:425`, after the session is committed. Not refunded, therefore counted: unknown email, account without a password hash, disabled account (`:385-399`, both the 401 and the 423 from `unknown_locks`); locked account with any password (`:401-405`, so a correct password during a lock is not an oracle and does not refund); wrong password, including the one that triggers the lock (`:409-412`); any exception before `:425`, including a failed `auth_settings` query, a row-lock or pool timeout and a failed commit (fail-closed). An expired lock followed by a correct password unlocks and refunds, which is a real success. An exception after `:425` (`roles_and_permissions`) refunds a sign-in whose password was correct; that is not a guess.
2. **Every failure path in `change_password()` is counted.** The hit at `:456` precedes all awaits; the refund at `:462` runs only when the current password verifies; a vanished user (`:459-460`), a wrong current password (`:463-468`, which also feeds `_count_failure` and the lockout) and any exception before the verify stay counted.
3. **Bursts.** Both checks and hits are synchronous with no `await` between count and hit, so on the single event loop concurrent requests are serialised at the counter: the sixth parallel request on an account, or the 31st on an address, is 429 even while earlier ones are still verifying. In-flight successes count too, so they cannot be used to burst. The API runs one uvicorn process (`api/main.py`, no `workers`); with more workers each process would keep its own counters (BL-65, documented).
4. **Refunds cannot reset the counters by alternation.** Proof of concept: alternating a correct sign-in to an own account with wrong passwords for other accounts from one address admitted exactly 30 failures, then 429 at request 60, address count 30; alternating correct and wrong passwords on the same own account admitted exactly 5 failures. A success adds one hit and removes one, so it is net zero; the only leak is the timing skew of finding 1.
5. **Lockout interaction.** The lockout is untouched and still caps guesses per real account at 10 per lock cycle (10 in 15 minutes, then a 30-minute lock that also ends sessions), well below the 5-per-minute account limit over any long period; unknown emails mirror it through `unknown_failures`/`unknown_locks`. The account key is the lower-cased, stripped email digest, so case and whitespace variants share one budget, and the lookup by exact email cannot reach a real account through a variant. Password-change failures no longer draw on the sign-in budget but still count toward the same lockout, so a stolen session plus sign-in attempts together still get at most 10 guesses per cycle.
6. **Password-change limit.** Keyed on the user id, so it cannot be bypassed by changing address or session; cleared in both test fixtures. No other route verifies a password (`verify_password` is called only from `identity/services.py`). The only unthrottled paths are the correct-password ones in finding 2.
7. **Client address.** `request.client.host` comes from uvicorn's proxy-headers handling with `trusted_proxies` defaulting to exactly the Compose proxy (`10.89.0.2/32`, BL-73), so the per-address limit is per client, not site-wide, in the shipped configuration.
8. **Documentation.** CHANGELOG entry, BL-83 note and the code comments at `services.py:44-49` and `:177-182` state the same numbers as the code.

## Author follow-up (`sec/M1-login-rate-followups`, pending re-verification)
- **Finding 1 (low):** `SlidingWindow.hit_at` returns the time of the count it adds, and `refund(key, at)` removes exactly that entry, if it is still in the window. `check_login_rate` and `check_password_change_rate` return a ticket of those entries, and `forgive(ticket)` gives back only them. Test: `test_a_refund_removes_only_its_own_count`.
- **Finding 2 (low):** every attempt, correct or not, also counts in `all_attempts` and is never given back: 20 sign-ins a minute per account (`LOGIN_ALL_RATE`) and 10 password changes a minute per user (`PASSWORD_CHANGE_ALL_RATE`). Test: `test_every_attempt_is_capped_even_correct_ones`. A cap on sessions per user is BL-84 (a).
- **Finding 3 (low):** `address_key` groups IPv6 addresses by /64 and IPv4-mapped addresses by their IPv4 address. Addresses also have an hourly cap of 100 failures (`LOGIN_RATE_IP_HOURLY`). Test: `test_addresses_group_ipv6_by_64_and_have_an_hourly_limit`. A site-wide alarm on failed sign-ins is BL-84 (c).
- **Finding 4 (info):** a password change at its limit answers "Too many password-change attempts". Listing 429 in the contract is BL-84 (b).
- **Finding 5 (info):** ADR-0007 amendment 1 now states the in-progress counting, the per-process scope and the caps. In section 8.2 the ADR reference is moved so that it covers only the login figures.
- **Finding 6 (info):** new tests cover failures mixed with successes (`test_failures_mixed_with_successes_keep_counting`), the address count given back on success (`test_successful_attempts_are_given_back`) and exact refunds. Unknown, disabled and locked accounts are never given back, because only the success path calls `forgive`.
