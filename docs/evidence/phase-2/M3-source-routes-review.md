## Data flows touched
- **Editor or admin to API:** a source (`name`, `url`, `config` per kind, jurisdictions, terms, `credibility`, `robots_policy`, `override_reason`, `terms_url`, `language`, `enabled`) and its nested job; or a job on its own. Gate: `sources.manage`; the override additionally needs `sources.override_robots` (admin only, `registries.yaml:10,31`).
- **API to DNS:** `validate_source_url` resolves every URL in the source at save time through `services.RESOLVER` (the system resolver in production).
- **API to PostgreSQL:** `source`, `capture_job`, `audit_log` in one transaction; `PATCH /sources/{id}` takes `SELECT … FOR UPDATE` on the source row.
- **API to reader:** sources and jobs to `sources.read` holders; later the admin UI (terms link) and the daily digest (override reasons).
- **Trust boundary:** every request field is untrusted, including from editors, who are not admins. DNS answers are untrusted.

## Findings

| 1 | high | **An editor without `sources.override_robots` can point an admin-approved robots.txt override at any other site.** `services.py:84-87` asks for the permission only when the policy or the reason changes. `url` and `config` (feed URL, page URL, crawl seeds and `allowed_domains`, endpoint) can change freely while `robots_policy=override` stays, and `_audit_robots` (`services.py:205-212`) writes no `source.robots_override` row because the policy and reason are unchanged. The approved reason names one site, but the override now applies to another. ASSUMPTIONS ("Others with `sources.manage` may still edit an overridden source's other fields") allows exactly this. The same applies to re-enabling (`enabled: true`) an override source an admin disabled. **Failure case** (`test_poc.py::test_a`): admin creates an RSS source on `approved.example` with override and reason "approved.example owner agreed in writing". Editor `PATCH {"config": {"feed_url": "https://other.example/rss"}, "url": "https://other.example/"}` gives 200; the source is still `override` with the old reason, and the audit still has one `source.robots_override` row. The editor can now crawl any site ignoring robots.txt (8.3, acceptance 4). SafeFetcher finding 22 (a) is therefore not closed. **Fix:** treat a change to `url`, `config` (or at least its URL fields and `allowed_domains`) or `enabled` on an override source as a new override: either require `sources.override_robots` or reset the source to `respect` and clear the reason for callers without it. Write `source.robots_override` with the URL fields in `after`, so the audit row says which site was approved. Add a test for retargeting by an editor (POST, PATCH of `url`, of each kind's URL field, and of `allowed_domains`), and correct the ASSUMPTIONS row. | | |
| 2 | medium | **Save-time DNS has no deadline and runs while `PATCH /sources/{id}` holds the source row lock and a pooled connection.** `update_source` locks first (`services.py:239`, `_source_and_job(lock=True)`), then `_source_values` resolves every URL one after the other (`services.py:155-158`, `check_config` loop at 64-67) through `validate_source_url`, which, unlike `fetch`, has no timeout (`policy.py:147-155`). A crawl source has up to 20 seeds plus `url`, so 21 sequential lookups. **Failure case** (`test_poc.py::test_g`, 0.25 s per lookup): the PATCH took 5.30 s, and a concurrent plain rename of the same source waited 5.10 s for the lock. With a name server the editor controls that never answers, glibc waits 5 s per try times attempts, servers and A plus AAAA, i.e. well over a minute per PATCH, each holding one of the 15 pool connections idle in a transaction. About 15 such requests from one editor exhaust the pool and every route that touches the database waits 30 s and fails. **Fix:** validate URLs before opening the transaction or taking the lock (resolve first, then lock and re-read); put one overall deadline on the save (for example `asyncio.timeout(5)` around all lookups, refused as `dns` when exceeded); resolve the URLs concurrently. | | |
| 3 | medium (latent until the UI shows it) | **`terms_url` is stored unchecked, so an editor can store a `javascript:` URL for the admin UI's terms link.** `schemas.py:85` is a bare `str`; `_source_values` never looks at it. 8.3 says the admin UI shows each source's terms link, and the web app uses React 18.3.1, which still renders `javascript:` in `href` (only a development warning). **Failure case** (`test_poc.py::test_e`): `terms_url: "javascript:alert(document.cookie)"` is saved (201) and returned as is. When the link lands, an editor gets script in an admin's session. **Fix:** require `http` or `https` and the 2,048-character limit for `terms_url` (shape only; it is not fetched, so no DNS is needed), and treat `url` the same way when it is empty (`""` is stored today). | | |
| 4 | low | **The refusal messages still tell internal names from unknown names.** `_REASONS` (`services.py:40-41`) hides the address, but "the host resolves to a private or reserved address" versus "the host name could not be resolved" is an oracle for which internal names exist, which the ASSUMPTIONS row says should not be possible ("cannot be used to map internal DNS"). **Failure case** (`test_poc.py::test_c`): `inside.example` (10.0.0.5) gives the first message, `nowhere.example` the second. An editor can enumerate `db.internal`, `vault.corp` and so on. **Fix:** one message for both reasons for names (keep the "private address" wording for IP literals, which reveal nothing), or accept it and correct the ASSUMPTIONS row; at least record the decision. | | |
| 5 | low | **The tests for IP literals pass for the wrong reason, so acceptance 3 is not proved by them.** The autouse `fixed_dns` resolver (`test_sources.py:19-28`) raises `OSError` for every host not in `HOSTS`, including `127.0.0.1`, `169.254.169.254`, `2130706433` and `::1`. Those cases (`test_sources.py:77-78,82,84`) are refused as `dns`, not as private addresses. They would still pass if `check_address` accepted loopback. The leak assertion (`test_sources.py:114`) only checks two strings in `message`, not `detail` or other fields. Production is correct: `literal_probe.py` shows all four plus `0x7f.1` refused as `private-address` by the real resolver. **Failure case** (`test_poc.py::test_b`): all four answer "the host name could not be resolved". **Fix:** let the test resolver pass IP literals through (`ipaddress.ip_address(host)` gives `[host]`) or use the system resolver for them, and assert the expected message per case; assert that no resolved address appears anywhere in the response body. | | |
| 6 | low | **The config is checked in its normalised form but stored as typed.** `check_config` validates `str(parsed.<field>)` (pydantic's WHATWG form) but returns and stores the raw dict (`services.py:60-68,156`, return value ignored). **Failure case** (`test_poc.py::test_h`, `unit_probe.py`): `http://feeds.example\@127.0.0.1/rss` is checked as `http://feeds.example/@127.0.0.1/rss` (host `feeds.example`) and saved raw. `urlsplit`, which SafeFetcher uses, reads the raw string as user info plus host `127.0.0.1`. Fetching stays safe as long as connectors use the parsed model or SafeFetcher refuses user info at fetch time, but anything that reads `source.config` raw (UI links, exports, a future connector) sees a different URL from the one checked. Tabs and newlines are also stored (`exa\tmple.com`). **Fix:** store `parsed.model_dump(mode="json", exclude_unset=True)` (or the whole dump with defaults), so the stored URL is the checked one. | | |
| 7 | low | **Free-text fields have no control-character or length checks, unlike M1 and M2.** `name` has only `max_length=200`; `override_reason` only the 1,000-character limit after trimming; `language` (a BCP 47 hint) has none (`schemas.py:76-87`, `services.py:78-83`). **Failure case** (`test_poc.py::test_e`): name `Feed` + U+202E + BEL, reason with U+202E (displayed backwards), a newline and an ANSI escape, and a 100,000-character `language` are all saved. The reason goes into the daily digest (8.3), where reversed text can misstate what was approved. **Fix:** apply `has_control` (newlines allowed in the reason if wanted) to `name` and `override_reason`, and bound `language` (for example 35 characters, BCP 47 shape). | | |
| 8 | low | **Out-of-range numbers give a 500 instead of 422.** `interval_seconds` has `ge=900` but no upper bound (`schemas.py:45`), and the column is `integer`; `page` has no upper bound (`routing.py:88`), and `(page - 1) * page_size` overflows `OFFSET` (`services.py:299`). **Failure case** (`test_poc.py::test_d`): `interval_seconds: 2**31` and `GET /sources?page=10**17&page_size=200` both answer 500 (`DBAPIError`, logged as `unhandled_error`). No detail leaks, but an editor can fill the error log at will. The page overflow is shared with `identity/services.py:702` and `admin/services.py:430`. **Fix:** `le=2_147_483_647` (or a sensible maximum such as 31 days) on `interval_seconds`; cap `page` in `PageParams` (for example `le=1_000_000`) or refuse an offset over a limit. | | |
| 9 | low | **Job checks run against an unlocked, possibly stale job row, and the cron check is shape only.** `_source_and_job` locks the source but reads the job without a lock (`services.py:201`), and `update_job` locks the job but not the source (`services.py:315`). `check_job` fills in the other schedule field from that stale row (`services.py:92-97`). **Failure case** (`test_poc.py::test_i`): with interval 3600, a `PATCH /sources/{id}` with `job.interval_seconds: 1800` (slowed by DNS) and a concurrent `PATCH /capture-jobs/{id}` with a cron: the job PATCH wins, then the source PATCH writes the interval next to the cron and hits the `CHECK ((cron IS NULL) <> (interval_seconds IS NULL))`, answering 500; its audit "before" would also have been stale. Separately, `_CRON_FIELD` (`services.py:37,100-102`) accepts `99 99 99 99 99` and an 800 KB field list (both 201), which the scheduler will have to handle. **Fix:** lock the job row as well (`with_for_update()` on the job query in `_source_and_job`, and lock the source in `update_job` in the same order to avoid deadlock); validate cron with the scheduler's parser (ranges per field) and cap its length (for example 100 characters). | | |
| 10 | info | **`RESOLVER` is a mutable module global.** `services.py:31`. It cannot be set from configuration, environment or requests; only Python code in the process can change it, and nothing under `api/src` does. Abuse in production would need code execution already. The risk is a future helper or fixture setting it outside tests, which would silently change the save-time policy for every request. **Fix (optional):** pass the resolver as an argument (default `None`) from a dependency the tests override, or have the app factory assert it is `None` when not in a test environment. | | |
| 11 | info | (a) Unknown body fields are silently ignored: `owner_user_id`, `health`, `consecutive_failures`, `id`, `created_at`, and `next_run_at`, `id`, `source_id` in the nested job are all dropped (`test_poc.py::test_f`: 201 with a fresh id, `unknown`, 0, `null`), so mass assignment is not possible; answering 422 on unknown fields would make client mistakes visible. (b) `render_js` is accepted whatever the `capture.js_rendering` feature flag says (`registries.yaml:84`); decide whether the API or the worker enforces it. (c) `GET /capture-jobs` is unpaginated (as the contract says); fine at the expected scale. (d) URLs that connectors may reach but which are not URL fields, such as `api_feed.params` values and crawl `allowed_domains`, are checked only at fetch time; acceptable, since SafeFetcher checks every hop. (e) `updated_at` is never changed on PATCH (no `onupdate` in `models.py`). | | |

## Checked and found fine
- **Gate:** every implemented route has `x-permission` (`sources.read` for the GETs, `sources.manage` for writes) and the gate is application wide. A viewer gets 403 on `GET` and `PATCH` (test). An editor cannot create a source with an override, set one on PATCH, or change the reason (403 before anything is written).
- **Override rules:** `robots_policy=override` needs a reason of 1 to 1,000 characters after trimming; switching to `respect` clears the reason; resubmitting the same policy and reason (also with surrounding spaces) is no change and needs no permission. The 403 is raised inside the locked transaction, so there is no check-then-write race on the policy.
- **Reason length and audit row for a new override:** a new override, on create or by a new reason, writes `source.robots_override` with before and after, in the same transaction as the change, besides `source.create` or `source.update`.
- **SSRF at save time:** every URL field per kind is checked: `rss.feed_url`, `web_page.page_url`, each `web_crawl.seed_urls` entry with its index, `api_feed.endpoint_url` when given, and the top-level `url`. `search_query` and `manual` have none. IP literals and numeric spellings are refused by the real resolver (`literal_probe.py`); a mixed public and private answer refuses the host. Refusal messages never name a resolved address; pydantic messages are produced with `include_url=False`, and the `url` reason only echoes what the caller typed.
- **Mass assignment:** `SourceWrite` and `CaptureJobWrite` have no server-owned fields, and connector configs forbid extra keys. `owner_user_id` is set from the principal; `kind` cannot change.
- **`q` filter:** parameterised `ILIKE` with `\`, `%` and `_` escaped and `ESCAPE '\'`. `' OR 1=1 --`, `%`, `_`, `\` and `F%` all match nothing; a 6,000-character `q` answers 200. `kind` is an enum and `health` a bound parameter.
- **Validators:** `ZoneInfo` refuses absolute paths, `..`, empty and directory names with `ValueError` or `ZoneInfoNotFoundError` (both handled), and `null` is refused by the schema before it gets there. NaN and infinity in `change_threshold_pct` are refused. The 2 MB body cap bounds config and rule sizes.
- **Error paths:** unexpected exceptions and unknown SQL states become a generic 500 with only a request id; 404s name only the kind of thing.
- **Delete:** disables the source and its job under the source lock, keeps rows and items, and a repeat writes no audit row.
- **Tests:** 26 pass. The override test does prove the 403s and the single audit row for a new override; findings 1 and 5 list what it does not prove.
